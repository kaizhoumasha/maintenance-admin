# 货架搬运业务接入层设计

状态:**阶段 A 已实现(`rack_scenarios.py`,含生命周期句柄、零接线默认实例与契约测试),文末决策记录以最新为准;真实联调/启用前确认项尚未关闭** · 依据:`wes_backend/docs/integration/manual-outbound-rack-transport.md`(2026-09-10 现场确认,下称「现场规则」)、`docs/superpowers/specs/2026-10-21-transport-outbound-design.md`(能力层,下称「能力层说明书」)

> 本层位于 `TransportService`(能力层)之上,工作线插件只调用本层。能力层不认识「进场/离场/五层货架」,本层不认识 HTTP、信封和重试。

## 1. 目标与边界

**目标**:把现场规则里确定的部分及明确标注的接口选择落成代码——货架角色决定每个场景用哪个 RCS 模板、源/目标位置的类型约束,并保证同角色的进出场模板配对。同一进出场生命周期的角色稳定性由调用方负责,本层不提供跨调用的生命周期强制约束。工程接口支持不等于现场合同已经确认,确认范围见 §3.3。

**非目标**:本层不认识任何上游业务单据,不判断为什么搬、何时搬、搬几次,入参都是调用方已决定好的事实(货架号、角色、目标位置、目标面)。留待后续阶段(见 §5)的有:目标点容量的滚动下发窗口、取消/失败后的业务重试、`departure_decide` 请求、换面时机判断、整架任务完成 API、任何需要入站结果(T3/T4)才能判断的状态。

## 2. 分层与位置

```text
工作线插件(只调用)
  │
货架搬运业务接入层   app/integrations/wms_transport/rack_scenarios.py   ← 本文

TransportService    能力层(已实现)
```

依赖只能向下;本层不读数据库、不发网络、不查任何货架状态(位置与面的有效性由 WMS 校验)。

## 3. 设计

> 本节的 `RackRole`、`enter_rack` / `rotate_rack` / `depart_rack`、`RackDestination`、`_move` 均为拟实现,**代码尚未编写**;已实现的只有能力层(`TransportService`)。

### 3.1 角色与模板表(唯一一份)

角色由调用方显式传入,**不得根据货架号前缀或位置编码猜测**(现场规则开头)。本层只定义自己的三种角色,不认识 `plan_delta`、`departure_decide` 等上游业务单据;由调用方的业务任务把业务字段映射成角色(现场规则中转运货架对应 `target_rack`、退料货架对应 `added_direct_picks`、五层货架对应 `bin_source_racks`,drain 货架也按五层货架处理)。

| 角色 `RackRole` | 进场 `enter` | 换面 `rotate` | 离场 `depart` |
|---|---|---|---|
| `TRANSFER` 转运货架 | `F01` | `CK04` | `F01` |
| `RETURN` 退料货架 | `F01` | `CK04` | `F01` |
| `FIVE_LAYER` 五层货架(含 drain 货架) | `CTU01` | `CTU02` | `CTU03` |

- 模板只在这一张表里出现一次;三个场景函数都查它,不各写一份判断。
- **同角色配对由映射保证**:传入相同角色时,离场与进场取自同一行,形成 `CTU01 → CTU03`、`F01 → F01`。调用方须依据权威业务事实固定同一进出场生命周期的角色并持续传入,不得每次从最新计划或历史任务重新猜测。门面不保存生命周期绑定,不能阻止调用方在两次调用间换角色；调用方接线验收须另行证明角色稳定,不得把本层映射测试当成端到端强制约束（D2 / 1A 已确认）。

### 3.2 生命周期句柄与三个场景

进场 → [换面…] → 离场是一个货架的一次完整操作。入口是 `RackScenarios.cycle(role=, rack_id=, caller=)`,返回不可变的 `RackCycle`:**角色、货架号、调用方只在创建时给一次**,三步共用,所以进离场模板的配对由构造保证,不会中途换角色;未知角色在创建时即被拒绝。

每一步在句柄上调用,各自使用调用方传入的会话,返回 `TransportHandle`,在调用方事务内登记,不提交:

| 步骤 | 方法 | 源 | 目标 | 说明 |
|---|---|---|---|---|
| 进场 | `cycle.enter(session, *, client_request_id, target, target_face=None)` | `Rack(rack_id)` | `RackPosition` 或 `Zone` | 模板取表中 `enter`;`target_face` 可选,原样传递 |
| 换面 | `cycle.rotate(session, *, client_request_id, position, target_face)` | `position` | `position` | 可重复(每个面一次);`position` 由调用方传入当前实际所在的精确位置,**只接受 `RackPosition`**,原样同时写入源与目标;模板取 `rotate`;不得根据计划目标推断当前位置 |
| 离场 | `cycle.depart(session, *, client_request_id, target, target_face=None)` | `Rack(rack_id)` | `RackPosition` 或 `Zone` | 模板取表中 `depart`;目标由调用方原样传入(如 WMS 的离场决定),本层不改写、不二次选址 |

**并发**:仓库里会同时有多个不同角色的货架在各自的生命周期里。句柄是冻结、`slots` 的值对象,不持有会话、不持有任何可变状态,创建开销可忽略;不同货架、不同角色的句柄互不影响,同一个句柄也可被多个并发调用方共享(各用各的会话)。唯一的共享对象是 `TransportService`,首次使用时从配置惰性取得依赖;登记流程中没有任何读取外部状态的步骤。**步骤先后不强制**(进场前离场、离场后换面都不会被拦住)——那需要持久化的生命周期状态,留到阶段 B。

目标位置统一收敛为两类:`RackPosition`(精确地码)或 `Zone`(库区),类型别名 `RackDestination = RackPosition | Zone`。进场与离场的区别只在取表中的哪一列模板,二者共用同一个内部实现(`RackCycle._move`),不各写一份校验与调用;`Rack`(货架引用)只作源位置,不作目标。

通用约束(来自现场规则与合同):`rack_id` 与 `RACK.location_code` 一致(能力层已校验);面是不透明非空字符串,`"90"`、`"270"` 原样传递,不做数值转换或去空格。

### 3.3 CK04

能力层按场景限定模板:`move_rack` 只接受 `CTU01`、`CTU03`、`F01`,`rotate_rack` 只接受 `CTU02`、`CK04`(`CK04` 仅换面可用)。默认模板:`move_rack` 为 `F01`;`rotate_rack` **不设默认、必须显式传**(评审 2026-10-22:五层货架要 `CTU02`,转运/退料货架要 `CK04`,一个默认值只对部分角色成立,漏传会悄悄发出错误模板;本层每次按角色表显式传入)。比合同 §3.2「不校验场景组合」更严,合同文本需同步。合同 0.4.0 §4.1 的文本仍只列 `CTU01/CTU02/CTU03/F01`,现场规则里也写明它「仍属独立合同」——**WMS 若不接受会以 `422 REJECTED` 返回**,按既有逻辑成为终态拒绝。联调前须与 WMS 确认,合同文本需同步。

- **RETURN 换面确认范围（D4 / 3A 已确认）**：角色表中的 `RETURN → CK04` 保留为本文选定的接口映射；引用的现场规则表只单列了转运货架的 CK04 换面,没有单独确认退料货架换面。WMS 确认及合同同步须精确覆盖「RETURN/退料货架换面使用 CK04」,不能把转运换面的确认直接当作该组合的确认。不新增本地拒绝规则或运行时开关；该项仍受既有真实联调/启用前确认门槛约束。映射测试只证明选定接口规则,不证明对端接受或物理完成。
- **进场 Zone 确认范围（D5 / 4A 已确认）**：`enter_rack` 接受 `Zone` 是本文已批准的接口泛化选择；引用现场表的进场目标只单列 `RACK_POSITION`，不能据此宣称具体现场的 Zone 进场约定已经核实。既有 WMS 联调确认及合同同步清单须明确核对进场 Zone 约定。保留 `RackPosition | Zone` 原样透传及既有测试要求，不引入位置编码猜测、额外查询、运行时开关或新的门面限制。

### 3.4 错误

沿用能力层异常:未知角色、目标类型不符 → `InvalidTransportRequest`;可信状态缺失 → `RackStateUnavailable`。不新增异常类型。
