## 1. 目标、选择与职责

在 smt_manual 的手工入/出库和 [smt_auto](2026-10-31-smt-auto-business-design.md) 的自动上架/拣料两方向内复用完整滚筒箱流和五层架流。每个业务宿主只有一份组件实例；自动两方向由宿主按原任务冻结 business_type 分派，BIN_Roller 不增加方向状态机，原生产及完成规则仍沿各流程合同。合并为一个真实组件，不在旧两组件外套包装层，不用单一长流程等待所有上游结果。

| 主体 | 负责 | 边界 |
| --- | --- | --- |
| 生产业务 | 任务/队列、计划/取消、供箱需求、当前任务及接续事实；SCAN2 业务准入、人工/自动作业、报告与任务完成；何时许可释放本次工作位箱 | 不编排五层架 CTU01/02/03，不重复受理扫码或创建 SCAN2 放行命令 |
| BIN_Roller | SCAN1～4 唯一公共事件入口及事实；供箱、分段投回、回流 FIFO、drain；普通/纯回收架统一生命周期；原箱流/架流动作、结果、pending 与恢复 | 不维护第二套任务生命周期，不决定逐盘授权/生产完成，不因模式添加四套分支 |
| 既有平台 | receiver/绑定/严格合同、事务、幂等、原业务结果通知、Outbox/Sender | 不改历史 wire/身份/冻结附录；不新增另一 Sender 或重试器 |

选择理由：投回箱、普通/drain 架、面服务及原动作收尾共享同一组事实和业务顺序，拆成两个可装配组件增加了不必要的分派与交还接口。合并仅收敛代码责任，事实、经过、面服务和原动作仍独立保存。

**禁止新增组件、宿主业务或内部模块的手工锁、位置预占/释放、通道租约、协调版本锁、缓存容量账及通用工作流。** 原平台 receiver、结果应用和发送器的既有事务/内部一致性保护保持。设备排队、运动、交接及物理互锁归 WMS/RCS/ECS/PLC。

## 2. 唯一组合、代码位置与原业务归属

严格事件/命令/WMS 请求合同随实际使用它们的 B2～B5 定义并在测试装配中验证，B7 只收敛 COMPONENT、正式加载及真实消费业务绑定；不能把正常动作所需声明全部推迟到 B7，或用临时宽松模型替代。唯一目标目录 `app/businesses/_components/bin_roller/`；静态 `COMPONENT` 的 key 为 `bin_roller`，业务只声明 `COMPONENTS = (bin_roller.COMPONENT,)`（有其他真实组件时按既有框架组合）。不再声明 bin_enter/bin_return COMPONENT，不嵌套组件，不新增动态生产插件目录。

内部按职责保留 `scan_flow.py`、`feed_flow.py`、`return_flow.py`、`rack_flow.py`，由 `service.py` 的 BinRoller 统一编排；共享表在本组件 `models.py`，不再规划根级 `app/businesses/rack_flow.py/rack_models.py`。合并前模块仅是未实施计划，不迁移不存在的生产表或重命名既有记录。

业务工厂用原 business_code/CommandOwner、原 capabilities 和本业务生产接缝构造一份 BinRoller，放在 `components['bin_roller']`。组件无业务码、独立工厂注册、PROGRESSION 或 Celery/Beat。原业务一个 `scan_pending` 公平推进生产待办及组件有界待办；父任务结束不停止原箱流/架流履约。

SCAN1/2/3/4 的 SCAN_COMPLETED 合同由同一组件唯一认领。共享 ECS 薄入口用 `require_component(ctx, 'bin_roller')`，四点都在 receiver 原事务保存本点事实，只有 SCAN2 同事务委托本业务生产接缝，不再让业务注册同键 SCAN2 装饰器。合同以 U04 已验证基线逐点适配并冻结版本，不能用空模型代替本系统声明。

合同、模型全局只加载一次，消费关系由 catalog 显式编译；不同真实声明撞键仍启动失败。新事件按受信绑定业务分派；WMS、ECS、Transport 结果按原持久业务关联唤醒，不按组件名/最新任务猜测。WMS 仍用 business_key=business:<原业务码>，Transport owner_domain 仍为原业务；历史 None 不回填，旧身份/字节/路由/期限/附录不改写。

## 3. 生产业务输入与 SCAN2 接缝

### 3.1 任务、供箱和接续上下文

生产业务保留任务真相源，提供本线当前执行任务有效性、原任务/版本的来源架面需求及精确追加/撤销、明确的接续状态/证据。组件不从箱码猜任务，也不把排队任务当当前任务。

任务/计划消息仍由业务自己受理；在其原事务将规范化本地供箱变化交给组件保存。变化关联原 message/receipt/operation 身份、task_id 和原成员版本，不新增外部字段、兼容 operation 或跨组件消息。取消区分未开始需求与本地在制段：在制段按到位物理事实继续请求 WMS，原清单/动作及归属按 §7 保留。

生产任务完成仍由业务裁决：按自己的原供箱需求/生产经过读取本业务完成条件所需进度；人工基线不把原 SCAN2 Result 作为整单确认统一前置，自动业务沿自身合同。原释放独立恢复，不等待组件全局 FIFO 排空或所有架离场；空查询/关联缺失不冒充完成。组件只提供只读进度和原结果，不返回统一“业务任务已完成”决定。

供箱进度沿已合并 supply_progress：有效需求以 feed_complete=true、pending=false 核对；未开始即撤销可返回 false/false，宿主须结合自己原成员的可靠撤销事实结清需求，不把撤销改记成功。已开始需求尚无 feed 时仍可 pending=true，原请求/清单/搬运及失败待处置继续。SupplyProgress 不带 withdrawn，不要求宿主查组件内部表；缺预期关联或无撤销依据的 false/false 不视为完成，也不把该进度扩为等待全局回流/架离场。人工映射见 [SMT 设计 §7.1](2026-10-31-smt-manual-business-design.md#smt-supply-completion)。

当前任务及接续读口使用调用方 session。接续 UNKNOWN/CHECKING/AVAILABLE/NONE 由业务按原 prepare/队列事实给出，组件不以“查不到任务”推导 NONE，不自行复制 prepare 调度。新任务使原 NONE 失效；未知只阻止新 drain 求值，不阻挡本点事实或无关合法动作。

### 3.2 SCAN2 到位到生产业务

组件先保存 SCAN2 原扫码、到位事实及本次原关联，再在**同一 receiver 事务**调用 `accept_scan2(ctx, arrival)`。业务接缝只保存自己的准入/生产待办，允许登记符合既有受理合同的本业务生产请求/动作 Outbox 意图；SCAN2 放行只能经 §3.3 的唯一方法登记；不提交、换隔离、另开推进事务或发 HTTP。组件不在委托前套用人工准入条件，也不因无当前任务自行放行；无任务/不可读等处置由该次业务接缝按自己的合同决定。普通业务不准入/关联异常不能抹掉本点事实；应作为业务状态可靠保存，存储错误仍按原协议回滚/重报，不宣称保存成功。

人工业务调用其准入/完工合同，自动拣料调用 bin.work_plan 等，自动上架调用 putaway.work_plan 等。是否允许缺 SCAN1、无任务如何处理、不可读箱处置及业务完成条件仍按各自合同；组件不设 is_manual/is_putaway 分支或统一业务授权状态机。

同一 arrival 只有一次成功提交的生产委托，标记、原事实和业务待办同事务保存；事务失败按原身份重报。委托成功即完成组件本次 SCAN2 受理待办；准入求值、WAIT 到期续问和生产完工由业务自己的待办推进，组件不再保存或消费第二份生产状态机。后续放行另有原 SCAN2_RELEASE 结果待办，不要求 SCAN2 受理项一直等到作业结束。完整旧消息继续技术幂等；已受理的新消息按本线本点相关事件流判断：相同业务扫码连续出现归原经过，之间有其他本点有效扫码/原动作 Result 则后一次是新进站。其他线、其他点位、ACK/心跳及重复旧 Result 不切分经过。原身份重报不重开生产，不新增或提升本点事实；无需等待独立离开或上游位置结果。arrival_id 仅为持久本地关联，不新增外部 visit_id。不可读准入和人工完成关联见 U04/U05。

### 3.3 生产业务决定释放，组件执行

生产业务在原作业条件满足时调用组件 `release_scan2(session, arrival_id=原本次到位)`；不能仅按 bin_code、当前任务或“最新到位”放行。组件核对原业务/工作线/本次关联，对原经过幂等登记唯一原 SCAN2 MOVE_FORWARD、原命令关联及结果待办，返回原 command_code。该生产业务本次已满足放行条件的 NO_WORK 等分支也经同一方法，不另写发送路径；组件不读取 NO_WORK 并统一立即放行。自动业务已结束取料但原取放/报告尚未收口时，仍由业务完成这些原义务后再调用。

生产业务唯一保存业务释放决定及原关联；组件只保存原命令/冻结设备和结果消费，不另建业务释放审批或决定状态，均归原业务并随调用方事务原子提交。重复释放取得原命令；迟到生产完成不能释放新经过。UNKNOWN/HELD 不重做。业务完成是否等待原放行结果沿各业务既有合同判断，可用组件只读原释放结果查询，不让业务重建/接管发送。

已有原释放命令时只返回/消费原命令；迟到生产完成或 Result 不改挂新经过。正常 release_scan2 返回原 command_code，不增加“旧箱先离开但原命令尚未执行”的 None/过期派发分支。

ECS 明确 callback Result 后才有原链后续执行，这是 ECS 与物理流程已有的推进保证，不由 WES 重建执行对象令牌、跨点等待或全线门禁。组件仍保存独立本点扫码事实，SCAN3/4 不回查上游任务/生产决定或新增上游 Result 等待。SCAN2_RELEASE 只消费原命令结果，不生成生产释放决定或补命令；UNKNOWN/HELD 不自动重做，FAILED 按原合同处理。

## 4. 物理事实、当前投影和原履约

| 记录 | 内容 | 规则 |
| --- | --- | --- |
| 原事实 | 本点原扫码/digest/设备/时间，或原 Transport/结果版本/实际终位/面向 | 事实先保存；业务任务无效、旧轮未结束或关联歧义不拒收实际到位；不可读不补预期箱码 |
| 当前投影 | 最近可确定的箱/架位置、面向及来源关联 | 原有效到位结果更新旧记录；依物理/RCS 互斥及原动作链，不建跨 Transport 排序器 |
| 原履约 | 原任务需求、完整分配、成员/段、经过、架周期/面服务、机会、请求/命令/Transport 及消费依据 | 原身份独立履约，不按当前任务/组件 key 改挂；流程结束不代替物理到位/离开 |

“当前”保存到位事实，不是位置许可。A 未离开时 B 不可能进同位由物理/RCS 保证；有效到位结果更新旧记录，不等旧离场回调，也不补造旧架去向。本项目不再建立通用跨 Transport 先后比较。已知失败终位仍可更新事实，失败不改成功；合法失败的明确终位从现有 outcome 读取；只有身份正确且终位明确的目标/面向不符架结果需要 U07 的窄位置接缝，不等待更正报文才承认该事实，也不据此履约成功。身份/种类不符及位置未知不提升为可靠投影，不直查框架表或收据诊断。

同箱/架确认后续到另一点位，旧当前关联退历史；不能两处同时记为当前，也不能清掉旧点后来到达的其他对象。重复原事实只返回原处理，不重新提升为当前；同次经过中迟到 INLET 结果不能回退已知 SCAN1/2。箱经过、回流轮次、架周期、面服务和批次身份分别保存，不靠箱码/架面查“最新”。

平台保存原 Transport/结果及既有成员事实，组件只保存原引用、已消费依据与本线当前投影，不另建一份 Transport 结果库；SCAN 原事实仍由组件持久保存。原动作应用与当前投影更新分别返回。CTU03 原请求取得明确接纳即可释放 WES 原周期；其最终 Result 迟到只补原历史，即使投影为 HISTORY_ONLY 也不重开周期；旧 CTU02 结果不能启动被后续事实超越的旧面动作。HISTORY_ONLY/NEEDS_ASSOCIATION 不是原动作失败或未履约。

回箱结果消费确认原成员已明确离开冻结交接来源时，仅将该原轮次已有放行动作的 SCAN4 当前投影退为历史；新经过、其他箱的新到位不受影响。部分失败中的已知终位同样可撤销旧投影，原批次失败/未决义务仍保留；不把位置变化当作整批成功，也不复制 Transport 的箱位账。

## 5. 箱流与回流

| 点位/步骤 | 行为 | 不增加的前提 |
| --- | --- | --- |
| SCAN1 | 实扫先保存；仅 -B 且本线当前执行任务有效则 MOVE_FORWARD 至 SCAN2，否则 MOVE_RIGHT 旁路 SCAN3 | 不匹配投箱成员/箱架绑定/来源资格，不等投箱位置/最终结果；成员取消不等于父任务无效 |
| SCAN2 | 组件保存到位，调用本业务生产接缝；有原释放决定才由组件登记原放行 | 不等 SCAN1 Result 才承认到位；具体准入归业务 |
| SCAN3 | 只按本点扫码/朝向分流并建立/识别回流 | 不查任务、生产决定或 SCAN1/2 Result；不继承上游 NG 原因 |
| SCAN4 | 保存到位/首次 FIFO 顺序；本点扫码/本次关联合法且无本点未决尝试即可唯一放行 | 不等 SCAN3 Result；关联不明先保存待关联，不强挂最新轮次 |
| 回架候选 | SCAN4 自身原放行 SUCCESS 形成进入回程缓存资格，取 1～4 箱物理 FIFO 连续合格前缀，非空即可请求，不等凑满四箱 | 不以扫码/ACK 代替自身成功，不过滤未就绪队头后跳箱，不要求同时停在最终取箱点 |

SCAN4 自身放行仅证明进入下游缓存。OUTLET 为统一交接入口，CTU/滚筒按冻结顺序连续取箱，WES 不逐箱再次放行、不建立缓存容量账。本点按用户确认的相关事件流保存首次有效到位/FIFO，连续重报不刷新顺序，不新增物理排序服务。

FIFO 先按当前物理轮次中所有尚未完成/未确认移出的物理顺序检查，再判断资格；不能在查询时先过滤当前未就绪或已分配/在途记录而跳到后箱。真正新 SCAN3 取代的旧物理轮次不继续充当当前队头，旧履约仍按原身份保留，不将其重新并入当前 FIFO。return_batch READY 只能分配原冻结候选的有序连续前缀，不跳号、不重排；未分配尾部保留原队列。READY 冻结本批成员与精确不同槽；同一物理前缀已有原未决请求时，其他普通/drain 面不得重领这些箱，由原 RETURN_BATCH 待办恢复，不改挂新面；原请求未知继续原身份，不重复分配。校验本请求成员/架面/槽位，不以所有历史活跃目标集合建立跨请求储位锁；储位与库存由 WMS 管理。ACCEPTED/CLOSED 不代表回架，原已应用成功及成员终位匹配才收口。

<a id="roller-return-rounds"></a>
已有轮次的 SCAN4 明确 FAILED 后只有 C07 全部条件满足的真实重扫才产生同轮新尝试，保留首次 FIFO 顺序；本轮 ACK/未知/超时/HELD 不授权重发。SCAN3 未决不阻止合法 SCAN4 放行。符合原本点分隔规则的真正新 SCAN3 独立建立物理轮次，旧履约、命令及冻结身份保留，不以旧轮闭合/人工移出作为前置。当前轮次取最新有效 SCAN3 的双向原关联；最新关联缺失/冲突不回退旧史，孤立旧历史不设全局门禁。SCAN3 不分隔 SCAN4 本点经过，新轮须取得自己的 SCAN4 匹配 SUCCESS，不能自动 VOID 旧履约或仅凭新时间戳重开。公共 [C07](../../integrations/workline-bin-return-api.md#return-rescan)与此合并行为一致。

## 6. 单一架流与完整生命周期

一个架周期记录原需求/供架来源、ORDINARY/DRAIN 服务目的、原 CTU01 及后续动作；它不是物理占位。两类架由组件内部**同一架生命周期入口**推进，不再按服务目的分派给两个组件，也不建两套 CTU01/02/03 状态机。首版目的和原任务归属在周期内固定：只支持同任务原周期多版本/面服务接续；跨任务及普通/drain 目的留场复用明确不做，见 §9.8。 普通周期面内既有投回交替不算目的转换；此排除只禁止新任务接管旧架周期或将普通/drain 互转，不按父任务切分公共 FIFO。原回箱机会仍按本线真实队首申请，箱来源任务完成/切换不取消合法回流；新任务承接本线遗留箱不等于接管旧架。

| 阶段 | 普通供箱服务 ORDINARY | 纯回收服务 DRAIN | 共用架流规则 |
| --- | --- | --- | --- |
| 进场 | 按原有效供箱来源登记 CTU01；可确定复用的在场原周期不因版本重放重复叫架 | 按原 drain READY 具体架登记 CTU01 | 原周期/意图稳定；不先占位，实际排队交对端 |
| 首次面 | CTU01 原目标面确认后直接开面 | 同左，直接纯回收面服务 | 不额外 CTU02；投影更新不自动再开一次面 |
| 投箱 | inbound_batch 完整最终清单按序拆为每笔 1～4 箱 BIN_MOVE | 不请求 inbound_batch、不创建 Feed | 原段成功/交接终位匹配才完成，不等扫码或可选中间事件 |
| 段间回箱 | 非末段成功形成 SEGMENT，一次最多一笔回架；成功/无候选/NO_BATCH 后续投 | 无投箱段，不伪造段间机会 | 同一组件内部依原步骤交替，无互相通知/交还协议 |
| 面末/纯回收 | 末段直接 FACE_END；最终 RACK_FACE_DONE 也直接面末服务、不造空投箱 | 到位即 PURE_RETURN，不等 feed_complete | 成功一笔仅完成该回架批次，有合法候选继续本面 |
| 面结束 | 本面供箱及原回箱/真实直接义务收口 | 无候选/NO_BATCH 且本面原义务收口 | 无候选不是全线排空；NO_BATCH 不是整架所有面结束 |
| 换面 | 仍有本架下一合法应服务面 | 仍有本架下一有序面且未触发 R01 真排空 | 唯一原 CTU02/RACK_ROTATE；确认返回原工作位/目标面后开新面，不重发 CTU01 |
| 离场 | 无下一应服务面且本架义务收口 | 末面收口或 R01 真排空且无本架其他义务 | departure_decide READY 冻结目标→唯一 RACK_MOVE/CTU03，WAIT/未知沿原合同，不硬编码去向或补造 target_face |
| 收尾 | 原 CTU03 明确接纳即释放本周期，生产/报告义务独立保留 | 原 CTU03 明确接纳即释放本周期；下一已到位架按自身条件服务，供架批次另行汇总 | 不等最终位置/Result；退出旧可服务架面关联，最终位置和运输由 WMS/RCS 管理 |

CTU02 绑定原面服务到下一面服务的转换，不只按目标面命名；合法 A→B→A 的第二次 A 不是重放第一次转换。同一原 CTU01/CTU02 结果重报不重复创建其原关联面服务；同任务新合法供箱需求先保存，不能覆盖旧完整 READY 或抢占其已选投回步骤；旧服务原义务收口且尚未登记离场求值时，可复用当前已到位同面，登记独立面服务引用而不新增 CTU01/CTU02。只有实际服务面改变时才按原转换创建 CTU02，不把“新服务引用”误当成必须换面。架流有唯一持久待办来源，feed/return/rack 内部方法不各自全量扫描同一周期并重复创建整架动作。

### 6.1 待办定位与统一推进

| 待办种类 | 可推进内容 | 不承担的内容 |
| --- | --- | --- |
| SCAN | 本点原事实/方向尝试及原结果；SCAN2 委托成功即结束受理项；SCAN4 成功后的原待回箱记录仍可作为本线求架检查的持久线索 | 不等待/消费生产准入或完工，不二次委托，不创建 SCAN2 释放；回箱待办不代表扫码位仍占用 |
| SCAN2_RELEASE | 原释放命令的公开结果/消费与恢复 | 不生成生产释放决定，不补建或替换命令 |
| FEED | 当前原面服务已选定的 inbound_batch/投箱段及其结果、原机会事实 | 不创建 CTU01/02/03，不独立开/关面或越过回箱步骤续投 |
| RETURN_BATCH | 当前原机会的 return_batch/BIN_MOVE 及结果 | 不另选架、换面、离场或独立开/关面 |
| RACK_CYCLE | 定位原周期并进入唯一 rack_flow 生命周期实现；处理原 CTU/departure 结果及步骤收尾 | 不复制箱批次的请求/结果消费；不垄断调用统一入口的资格 |
| DRAIN | drain 供架请求/原 READY 批次；幂等关联原架周期、记录未用项并读取周期进度收批 | 不自行实现 CTU/面转换、不递归扫描已有周期；选中启动的周期由 service 交唯一架流入口启动 |

普通供箱需求和 drain 中已选用/原进场已登记的架都只幂等关联同一种 RackCycle；drain READY 的其余项先保留原候选，不因返回了多个架就全部启动进场。服务目的只决定面内投/回箱步骤。六类待办用于定位原事实和原记录，不是六个隔离的调度器：service.advance 先让所属模块幂等消费本次原结果，再在同一调用方事务将受影响的原周期交给唯一 rack_flow 生命周期入口。FEED/RETURN_BATCH 不复制换面/离场决策；架流入口不二次消费箱搬运结果；本次明确关联周期的原 CTU/departure 公开结果可在该入口幂等处理，不因当前 work 是 FEED/RETURN_BATCH 等而留到另一轮。DRAIN 选中启动的周期也由 service 交该入口登记初始动作，后续仅读取周期状态收批，不全批递归推进。

统一入口可继续本次原周期已经就绪的本地步骤，并调用 feed_flow/return_flow 的普通幂等登记方法，把下一步骤引用及其所需首个原 Outbox 意图一起保存；到真正等待原请求、搬运、设备结果或业务决定时停。无需先提交“选择步骤”、再等下一条待办/下一次 Beat 登记请求；无候选、末段完成、同面接续等本地状态变化也不额外等一轮。调用方向固定为 service → 原结果消费模块 → 返回进度，再由 service → rack_flow → feed/return 登记普通方法；feed/return 不反调架流或递归 advance。只处理本次有明确引用的原记录，不能凭箱码/当前任务猜原架周期，不递归其他 pending、不另开事务或全批扫描，不新增私有通知/调度器。周期待办用于原结果恢复和兜底，重复入口调用仍复用已选原步骤，不重复动作；步骤关联是履约进度，不是通道许可、占位或锁。

待办发现复用现有业务的游标扫描方式：原业务短会话读取六类待办各自本轮最大 ID，然后在各类上界内按稳定记录 ID 分页，生产与组件各类页面公平轮换；单条推进仍用业务自己的独立事务。即使本页全在等待、推进无变化或单条失败，游标也向后走，不能每次只扫最前 limit 条。新产生工作由后续原结果通知/Beat 发现；该上界只限制候选发现，不把本次已选本地后继及首个意图推迟到下一轮；上界和游标只在本轮内存中使用，不持久化为协调状态。记录 ID 排序只用于候选遍历，不代表物理先后或 SCAN4 FIFO。

### 6.2 机会、面服务及业务步骤

机会 kind=SEGMENT/FACE_END/PURE_RETURN。一个机会与一笔回架批次不是同一记录：SEGMENT 最多一笔，FACE_END/PURE_RETURN 可连续多笔。每笔批次分别保存原候选、operation_id、BIN_MOVE 及消费依据；FACE_END/PURE_RETURN 的下一笔以原成功 batch.id，或已消费且尚未创建 Native Transport、物理候选已过期的原 batch.id 为既有后续来源，继续当前 FIFO；旧候选/请求保留，不伪造成功。SEGMENT 仍最多一次，过期原候选消费后继续原供箱步骤。未知请求或已建 Native 的原义务仍沿原身份恢复，NO_BATCH 已结束的机会不能借新批次重开。

统一 rack_flow 入口根据本事务内已保存的本面机会进度选定首笔/下一笔本地批次引用，并同事务调用 return_flow 登记该引用的原候选/请求；RETURN_BATCH 随后只消费其原请求/搬运结果。原已完成批次重扫只返回自身进度，不自己另发下一笔，也不关闭面服务。当前批未收口不得选定下一笔，同一已选后续步骤重复推进复用原引用；下一批的引用/首个意图与前批消费、机会进度在同一原推进事务保存，这些都是原履约关联，不是资源占位或新的流水线引擎。

SEGMENT 成功一笔回架即结束机会；FACE_END/PURE_RETURN 的单批成功只更新批次，继续本面候选，直到无候选/NO_BATCH 且原义务收口才结束面。末段不同时生成 SEGMENT 和 FACE_END。NO_BATCH 不定时重试、不因重扫/新箱/重复唤醒重开；另一段成功或新合法面服务才有新机会。

正常回箱机会按以下事实分支处理，不将它们混成一个“等待排空”状态：

| 当前事实 | 正常处理 |
| --- | --- |
| 本机会已有原请求/分配/搬运未决 | 只恢复该原步骤，不另发请求，也不能当无候选跳过 |
| 未登记请求且有 1～4 箱合法连续前缀 | 立即按该前缀请求；不等四箱、后续扫码、整条 FIFO 排空或缓存总容量配置 |
| 未登记请求且当前无可请求前缀 | 保存本机会 NO_CANDIDATES，不发送空请求、不伪造 WMS NO_BATCH；段间直接续投，面末/纯回收在本面直接义务收口后结束服务，不等后续新箱 |
| 原 WMS 明确 NO_BATCH | 结束本机会，按 SEGMENT/FACE_END/PURE_RETURN 的原步骤继续；不在同面定时续问 |
| 整条 FIFO 及本段原料箱分配/在途/未决义务确实清空 | 才可按 R01 真排空收尾；无候选或单面 NO_BATCH 不能替代这个事实 |

原依赖须是具体原请求/Transport、周期/服务及相关资源，不能按同线同名架面全部历史 UNKNOWN 阻挡实际新到位。通道只保存原执行步骤，不设置 BUSY 租约、目标预占或空闲许可。普通取消不跳过原已授权义务，也不伪造 feed_complete。

### 6.3 drain、提前排空及批次收尾

正常求架由宿主独立 advance 从现有本线待回箱记录发现，不要求先有 DRAIN/架周期：SCAN4 自身成功、新接续事实提交后的原业务即时推进、原普通服务/架周期收尾时，service 在同一 SERIALIZABLE 推进事务检查本线当前 FIFO 与原服务。能够沿合法原普通面步骤或原 drain 批次继续时先推进原流程；需要新供架时，只有业务明确 NONE 且当前有非空可请求 FIFO 前缀才登记唯一原 drain 请求，数量按原合同取本段当前需回箱数作参考，不把最多 4 箱的单笔 return_batch 上限当作整批供架数量。

本线无架且接续 UNKNOWN/CHECKING/AVAILABLE 时，不把“SCAN4 命令已成功”误作整轮责任完成：已有原待回箱记录继续作为 list_pending 的恢复线索（复用 SCAN4/回流原记录，不加待办种类、调度表或私有通知）。后续原业务事件/结果及 Beat 能重新检查；条件已满足时同事务登记求架意图，不额外等一次定时扫描。原请求/供架批次已存在则继续原身份，不重复申请。这个判断只决定新供架，不把旧架记录当全线忙碌许可。

队首未就绪不等于可以跳箱或先申请空批供架。NONE/接续状态只用于决定新的 drain 供架请求，不是已登记进场、当前面回架、换面或离场每一步的前置；任务切换不暂停原周期。READY 提供可用架/有序面，不冻结整批箱或预留容量。先按原选择使用需要的候选，未选候选不提前登记 CTU01；一架服务结束后仍有可请求箱，优先选本批剩余候选再启动原进场，而不是立刻申请新批。已登记其他进场原动作仍照原身份履约，其他架先实际到位也不被预期选择顺序挡住。原架集合无序时保存原选择；已提交其他架先有可靠实际到位时照常保存/处理事实，不要求本批全部架结果到齐。

无候选不能冒充真实排空；SCAN4 未决、原料箱分配/搬运在途仍保留责任。R01 排空判断针对本段料箱，不以其他架尚未到位或尚未创建离场动作否认箱流已排空；这些架的原义务分别影响其周期及供架批次收尾，不反过来造成“先等批次完成才能排空”的循环。R01 真排空时已到位架无其他义务即可正常 CTU03，不逐空面。仅 READY 但尚未创建原 CTU01 的候选记录未使用，不为空跑补进出场；已创建 CTU01 的未到位架沿原动作收口，迟到后正常离场，不自动撤销。

箱回架、面服务结束、回程排空、WES 原架周期释放和本批供架结束分别判断。本批应服务候选已完成原服务（真排空时未启动项记未用）、已创建进场/换面等原义务收口且应离场周期的 CTU03 已明确接纳后，WES 本批供架可完成；不能只看已建周期都释放就漏掉仍需服务的本批未选候选。仍有箱则重新取得业务接续依据申请下一批，不等这些 CTU03 的最终位置/Result。FIFO 排空或面结束不能代替尚缺的进场/换面事实和离场接纳；仅 CTU03 已接纳也不代替本批其他架/回流义务完成。同一次原周期进度更新后，service 可调用 return_flow 的原批次汇总方法收尾所属 drain 批次，再检查下一正常求架条件；只读原关联周期进度，不推进其他周期，不等待 DRAIN work 下一轮才把本批标完成。父任务结束不丢原 pending，CTU03 接纳后的平台运输记录与 WES 周期待办分开。

CTU01 明确拒绝/失败且未到位不虚构面服务或 CTU03；CTU02 失败不标新面就绪。CTU03 接纳前拒绝/未知不释放，沿原合同和身份处理；明确接纳后不等待其最终结果，后续失败/异常由原 Transport 与 WMS/RCS 处理，不回滚 WES 已释放周期或自动重发 CTU03。

### 6.4 CTU03 接纳即释放的具体边界（用户已确认）

1. 原 departure_decide READY 仍是离场业务决定，之后只创建一条冻结目标的原 RACK_MOVE/CTU03；本地创建、发送开始、READY 本身均不作为接纳。
2. 通过既有 Transport 公开结果读口核对原 transport_task_id/client_request_id/caller 及原 submit 的有效接纳响应：202/RECEIVED 或 200/DUPLICATE。不凭 Outbox 状态或裸 HTTP 200 猜测。已有原有效成功执行结果时可幂等补收原释放，不要求再次等接纳报文。
3. 接纳后在原业务事务保存原接纳消费依据，完成 WES 周期，退出该周期的可服务架面/旧在位业务关联；允许后续供架及本批收尾。只退出原关联，不清后来到位的新架，也不建立“名额释放”或资源占位表。
4. WES 不需要 CTU03 最终位置，不推定货架已到某库位；最后实际到位及原离场接纳留历史，目的地运输/实际终位由 WMS/RCS 管理。平台原 Transport 可继续接收结果/告警，但组件不为最终终态保留阻塞 pending，也不把该已接纳离场作为下一独立周期的未闭合前序。
5. 最终 Result 重报/迟到/失败只关联原 Transport，不重新释放、不恢复旧可服务面、不清新架、不自动发第二次离场。接纳前的明确拒绝或接纳未知则保留原待办，不能冒充已释放。

此处只调整五层架 CTU03（普通/drain 一致）。CTU01/CTU02 仍按实际工作位/面向到位；料箱 BIN_MOVE 的回架成功、成员终位及既有位置前置保持，不把 CTU03 的接纳边界自动扩到它们。

### 6.5 正常场景逐步推演与动作核对

以下是设计推演，不是联调或现场记录。“成功”均指原合同要求的匹配权威结果、终位及适用位置前置已满足；CTU03 的“接纳”按 §6.4。数量是示例中 WMS 的实际决定，不用于 WES 推算架槽容量。面标识 A/B 假设由 WMS 原样返回，不增加面向枚举限制。

#### 普通架：5 箱分为 4＋1，段间一批、面末多批

本例只有当前供箱面 A，初始回流 FIFO 有 6 箱合格候选；WMS 后续按表给出分配。

| 顺序 | 原动作/结果 | 组件下一步 |
| --- | --- | --- |
| 1 | CTU01 到 A 面；一次 inbound_batch READY 返回完整最终 5 箱 | 直接开原面服务，不补 CTU02；保存整份清单，不分页重领 |
| 2 | 第一段投 4 箱成功 | 形成唯一 SEGMENT 机会，同事务登记其首个 return_batch 意图，不等这 4 箱扫码/生产完成 |
| 3 | 该次 return_batch READY 仅分配 FIFO 前 2 箱，原回架成功；FIFO 尚余 4 箱 | SEGMENT 已执行一笔即结束，直接登记第二段投箱，不再追加段间批次或等待 FIFO 排空 |
| 4 | 第二段投余下 1 箱成功 | 直接进入 FACE_END，不再同时建一个 SEGMENT |
| 5 | 面末第一批 READY 分配 2 箱并回架成功；FIFO 余 2 箱 | 当前面末机会保持，登记不同身份的下一批，不重复首批原请求 |
| 6 | 面末第二批 READY 分配 1 箱并回架成功；FIFO 余 1 箱 | 当前面末机会仍保持，核对最新队首再求下一批 |
| 7 | 下一批 WMS 明确 NO_BATCH | 结束本面机会/服务；余 1 箱保留原 FIFO，不在本面轮询 |
| 8 | 无下一应服务面，原直接义务收口；departure READY，CTU03 明确接纳 | 释放本架周期；不等余箱回架、生产工作结束或 CTU03 最终结果。余箱由后续合法普通架服务或满足条件后的 drain 承接 |

核对本例：CTU01 一次、CTU02 零次、CTU03 一次；inbound_batch 一次、投箱 BIN_MOVE 两笔；return_batch 四次（3 个 READY、1 个 NO_BATCH），回架 BIN_MOVE 三笔。所有原结果重报均不增加动作。READY 已是最终清单，投完不再为“确认还有没有箱”补问 inbound_batch；若原响应本来就是 RACK_FACE_DONE，则直接面末服务，不造零箱 BIN_MOVE。

#### 同任务同面接续：新需求复用到位，不覆盖旧服务

1. 上例旧清单尚未完成时，同任务新 revision 增加当前 A 面需求：先保存新需求及原版本引用，旧 5 箱清单与已选投回步骤不变。
2. 旧面服务按其原机会/直接义务收口后，若离场求值尚未登记，统一架流入口看到新合法需求，就在当前实际 A 面创建新服务引用，发该新需求的 inbound_batch；不发 CTU01/CTU02/CTU03，不重新等待原到位回调。
3. 假设新 READY 完整返回 2 箱，则一笔投箱成功后直接 FACE_END，之后按本服务机会回箱/结束。旧服务的 NO_BATCH 不作为新服务的分配结果；合法新需求是新服务依据，不是只换 operation_id 重试旧机会。
4. 后续仍按同一周期选择合法下一面或离场。若原离场求值已经登记（含 WAIT/未知），则继续原离场步骤，不能插入供箱、撤销离场或把新需求标为已完成；此边界保持 §9.8 原规则，不等待生产段/全局 FIFO 排空来决定能否复用。

核对复用边界：新增的是需求/服务/请求身份，架周期和实际到位继续沿原事实；重复新计划、旧 CTU 结果或旧回架结果不重复开新服务。

#### drain：两架、多面回箱，各架独立离场，本批另行收尾

本例业务接续明确 NONE，FIFO 有 6 箱可请求；一次 drain READY 提供两架，各自有序面为 A/B，本例先选用第一架并实际到位，第二架先保留原候选，待需要时启动。

| 顺序 | 原服务 | 结果与接续 |
| --- | --- | --- |
| 1 | 第一架 CTU01 到 A；PURE_RETURN READY 分配 2 箱并回架成功 | 不请求 inbound_batch；仍有 FIFO，继续同机会下一批 |
| 2 | A 面下一批 NO_BATCH；原义务收口 | 只结束 A 面，登记该架唯一 CTU02 到 B，不重发 CTU01 |
| 3 | B 面 READY 分配 2 箱并回架成功，下一批 NO_BATCH | FIFO 余 2 箱；本架面已用完，departure READY/CTU03 接纳即收第一架周期，同事务选本批第二架并登记原 CTU01，不重复申请 drain；不把 NO_BATCH 当全通道排空 |
| 4 | 第二架 CTU01 到 A；READY 分配余下 2 箱并回架成功 | FIFO 及本段原义务确实清空，按 R01 结束；不切空 B 面，不发 required_slot_count=0 或为求 NO_BATCH 再问一次 |
| 5 | 第二架 departure READY/CTU03 接纳 | 收第二架周期；本批所有原服务/进场等义务已收口才完成 drain 批次，不等任一 CTU03 最终结果 |

核对本例：drain 供架请求一次；两架各 CTU01/CTU03 一次，只有第一架 CTU02 一次；return_batch 五次（3 个 READY、2 个 NO_BATCH），回架 BIN_MOVE 三笔。第一架接纳离场后，下一已实际到位架按自身条件服务，不等本批全部架到位或最终运输完成。最后一架接纳若已满足本批收尾条件，同事务汇总本批并检查新的接续事实/当前前缀：仍有新合格箱才申请下一批，不与本批重复申请，也不为本地批次状态更新另等一次 DRAIN work/Beat。提前排空时，未创建 CTU01 的其他候选记未使用；已创建进场动作的原架到位后按原周期正常离场，不新增撤销/补空面流程。

#### 四类生产业务：同一 SCAN2 入口，不同业务许可时机

共同起点是组件先保存原到位、成功委托一次后收口受理项。下表是生产接缝的责任，不在 BIN_Roller 写四类分支，也不据此声明四个完整生产包已交付。

| 生产业务 | 本次准入/生产推进 | 调用唯一 release_scan2 的时机 |
| --- | --- | --- |
| SMT 手工线拣料 | 按[人工准入/完工合同](../../integrations/manual-picking-api.md#manual-admission)，WORK_REQUIRED 保存原关联，等唯一匹配完工；WAIT 由业务在原到期点后新求值 | 合法 NO_WORK 直通，或原匹配 NORMAL/NG 完工已应用；不等公共 FIFO/货架离场 |
| SMT 手工线上架 | 沿同一人工基线，保留原任务 business_type/本次经过；不借组件新增上架特判 | 按该原人工准入/完工决定，仍只调用同一释放口；不另发第二份命令 |
| 自动线拣料 | 按[自动拣料合同](../../integrations/smt-auto-api.md#scan2-release)取得 work_plan，再处理原逐盘授权/报告 | 本例首问 NO_WORK 且无旧义务可正常释放；有生产时明确无后继、无待消费授权且本箱原义务结清。单盘报告收妥本身不放箱 |
| 自动线上架 | 按[自动上架合同](../../integrations/smt-auto-api.md#scan2-release)，有任务且 source_racks=[] 也先请求 work_plan，由 WMS 决定 WAIT/NO_WORK，不等补架再首次上报 | 有效 NO_WORK 或末盘 ACCEPT 省略 next_source_action 先结束新取料；原已授权取放/扫码/决定及报告仍按本箱合同收口后才释放，不补箱尾 work_plan/额外 clearance 请求 |

WAIT 的合法新求值不是再次调用 accept_scan2，也不是新扫码经过：保留原 arrival/task/bin/scanned_at，按各业务合同只更新允许变化的求值事实和新消息身份；未知技术重试仍保留原消息/正文。无任务时也不套共同动作：已确认人工基线不请求/不自动放行，自动上架按其合同正常放行（原已有授权另行收口），不编造 task_id。

核对共同尾部：业务保存许可与原关联并调用组件，组件同事务登记一个原 MOVE_FORWARD/结果待办；重复许可、重复完成、重复通知只取得原 command_code。命令结果由 SCAN2_RELEASE 独立消费；实际 SCAN3/4 继续按本点事实处理。组件层只验证许可前不擅放、许可后唯一放行及原身份恢复，不在测试适配器里复制四套完整生产链路。

## 7. 事务、取消、恢复与通知

四点受理及 SCAN2 本地业务委托使用 receiver 原事务，保存事实、原关联、决定和持久待办。新动作只在相应合同许可下登记原 Outbox。业务的单条独立推进事务负责统一结果快照、原消费依据/组件进度/生产释放决定/下一意图原子保存；内部方法用调用方 session，不提交、不另开竞争事务、不发 HTTP、不手工取锁。平台原隔离/幂等及错误重试机制保持；不通过宿主新增锁补回占位。

取消停止尚未开始的新需求，不终止仍在执行的本地任务/段；原架/箱到位后仍按原上下文和实际事实请求 WMS，依合法决定继续原段。原请求未决恢复原决定，READY 完整清单及剩余段不剪裁；不以取消和 READY 到达顺序作统一截断点。取消后原架到位照存，按物理先后更新投影；旧事实只补原动作，新任务不改原 owner/身份/服务目的。同任务新版本按原周期续面；已经登记的换面或离场求值（含 WAIT/未知）继续原步骤，不被新计划改写。首版明确不做跨任务/目的留场复用，不自动接管/丢弃/重开原周期。

新事实/原结果提交后仅唤醒原业务；消息只表示“重查该业务待办”，不代表某个步骤已完成或获准再执行。组件不发布私有通知；after_commit 的外层提交/回滚语义、1 秒连接预算、无发布重试及 5 秒 Beat 保持。业务公平扫描生产作业和组件的扫码/释放、供箱、回架、架周期/drain 待办；组件内部有界且无变化不自唤醒。通知可丢可重，恢复只用原身份，不按最新任务/箱/架查替代动作。

Transport 原 submit 有效 RECEIVED/202 或 DUPLICATE/200 接纳保存为 DONE 时，主应用已有 on_delivered 事务端口按原 operation_id 与 business_key=transport_task_id 读取原 owner_domain，经 after_commit 唤醒原业务；有效结果应用仍沿原结果通知。失效租约、重复完成、失败/未知接纳、无已知 owner 和回滚不误通知。通知失败保留原接纳/持久 pending，原 RACK_CYCLE 由同入口 Beat 恢复。CTU03 读取公开接纳释放 WES 周期，不等最终 outcome/位置；接纳不证明物理运输完成，组件或宿主不另加通知器和调度器。

### 7.1 原业务身份与幂等登记

同事务保存消费进度、原业务记录和 Outbox；重复执行用相同业务身份查回原记录。receiver 只判完整消息身份，ECS/Transport/Outbox 只判各自原调用身份，不会自动合并两个不同随机 ID。BIN_Roller 只为下面真实业务对象定义必要唯一约束，不另建通用“父进度→后继”登记层。

| 业务对象 | 唯一性与恢复依据 |
| --- | --- |
| 原扫码事实与经过 | 沿现有 ctx.digest 原样保存每条事实及其 arrival 关联；以本线本点、原分隔依据及原扫码业务内容确定本次经过；同一依据只登记一次，不以“当前未收口经过”兜底合并。原消息重报读原关联，不刷新首次到位/FIFO；不能只保存首条摘要而漏掉连续消息的关联 |
| SCAN2 委托/释放 | 同一原 arrival 的委托只成功提交一次，释放沿该 arrival 的稳定 call_key；已有命令读回原 command_code，不再生一份许可或命令 |
| 供箱/机会 | 原面服务的 inbound 请求、原完整清单内的段序、原段/面服务对应的回箱机会分别唯一；同任务新合法需求有自己的服务引用，不按架号/面名吞掉新需求 |
| 回架批次 | 原机会/原已选回架步骤保存其单笔原请求；FACE_END/PURE_RETURN 下一笔由原成功批次，或已消费且未建 Native 的过期物理候选批次触发，沿其原 batch.id 定位；SEGMENT 最多一次。重复处理复用同一业务输入的原意图，不另发序号，不遍历请求来源链 |
| CTU01/02/03 | 原周期的入场/离场、原周期内该次面转换分别唯一；转换依据保留原服务引用，A→B→A 的两次转换不合并。动作已有 client_request_id 就沿原 Transport 接口恢复 |
| drain 供架/候选 | 实际求值记录保存原 operation_id/消息引用；READY 执行按原 operation_id 唯一。一次真实求架输入只登记一个原意图；不设 FIRST、请求来源链、线级根记录或 open 排他索引 |

必要唯一约束在 BIN_Roller 自身业务表声明，与业务记录/原意图同事务登记；冲突沿原接口及原事务恢复。不同 work 指向同一业务对象时使用相同业务键，不能先各造子记录再指望 Outbox 合并。正常按原记录 ID/业务状态保存进度仍属业务持久化；不为制造写冲突而改写原父记录或本点前驱，不引入父后继表、共享头指针、流版本、CAS、忙碌位或租约。

本点经过按 U02 的既有事实规则辨别，不按任务、箱码或 active 状态寻找一个旧经过兜底：

- 完整技术身份先查 ctx.digest 的原关联；命中时返回原经过，不把重报当作当前新扫码。
- 对新技术消息，从本点原扫码事实/经过关联读取最近的业务经过。业务内容连续相同且无新的有效分隔则归它；不同业务内容形成新经过，以前一经过的持久引用作为分隔依据，不以其最后一条技术重报摘要作边界。
- 同内容在该经过的原本点动作新有效 Result 后再来，形成新经过，依据是原命令及其已应用 Result 的原身份。直接使用既有原 command_code 与公开已应用 Result 识别分隔，不把每次回调 receipt_id/新消息 ID 当新边界，也不要求平台增加接收时刻或全局序号；公开 Result 已存在即可辨别，不等 Beat 消费。该 Result 已用于后一次经过后不能再次充当新事件；旧经过的迟到/重复结果只按原关联补历史，不从历史中重取“最后一个 Result”切分当前经过。
- 经过业务键只表达本线本点、上述原分隔依据和原扫码业务内容；首次使用同一“无前序事实”依据。保留参与判等的原始码/原字段，不能把不同原码均解析成 None 后合并；当前任务、drain 状态、旧经过或回流轮次是否收口均不制造或否决新进站；新经过先按本点事实保存，轮次关联/动作许可仍沿原合同，不以此伪造旧轮完成。分隔依据随该经过保存，重启后沿原记录读取，不生成新外部 visit_id、时间窗口或流序号。

这里只保存每次判断的原事实引用，不维护可抢改的本点头指针/流版本。业务键唯一冲突只合并相同创建依据的同一经过；不能因键相同就无条件覆盖输入或返回旧经过，必须核对原作用域/依据/内容及原消息关联。已经看到新分隔事实却算出旧键属于判定错误，不能把真实新扫码吞成重复。两条等价消息并发登记，由该业务唯一约束与原事务恢复合并，事实/关联/委托一起提交。

供架恢复沿 manual-picking 的两层实际业务查询语义：[DrainRepository.current](../../../../wes_backend/workline_plugins/manual-picking/src/manual_picking/application/drain_repository.py)先找本线原 READY 执行及其原求值，再通过结果读口找原待决/WAIT 请求；[decide_in_session](../../../../wes_backend/workline_plugins/manual-picking/src/manual_picking/application/drain_flow.py)恢复原未决，WAIT 到原到期点且仍有需要才新求值。移植的是这个行为，本项目只查询组件自有业务记录、经现有 WmsRequests/Transport 公开读口取原结果；不直查框架表，不复制原项目的 WorkLine 锁、独立 Scheduler、占用窗口、checkpoint 或按历史链找末端的机制。

当前查询不以“有无历史”授予许可。按原作用域核对实际 READY 执行、尚需处理的原求值/尾部阶段；它只给新需求评估提供业务进度，原回调/原 work 始终按自己的原 ID 消费。不能将尾部查询当物理排序，也不遍历更旧的任意 UNKNOWN 记录来充当当前。

| 读到的实际原业务事实 | 本次处理 |
| --- | --- |
| 有本次 READY 原义务，或 READY 已返回但业务尚未消费/建立执行 | 先恢复/消费这笔 READY 及其原执行；不因暂时无 ACTIVE 行再求一批，不等另一条待办改状态 |
| 当前原求值尚未消费到合法 READY/WAIT | 按其原 operation_id/message_id 读结果或恢复原发送；不按当前队首重新注册 |
| 原 WAIT 已消费 | 不刷新原到期点；到期且当前确有需求才登记这一原 WAIT 的一次合法重问 |
| READY 已消费且 WES 本批原义务已合法收口 | 当前可以无在制供架而历史仍保留；有新合法需求就评估新请求，不等历史删除或 CTU03 平台最终结果 |
| 本次事务查询未见本作用域原求架记录 | 只进入本次首次登记的候选分支；完整判定/唯一性/依赖校验及成功提交后才成立，不证明旧事务已回滚；FIFO 只提供本次需求/参数 |
| 查询失败、已有请求缺失必要原关联或结果不合法 | 不当作“没有记录”转入首次登记；沿原技术回滚/业务异常处理，不增加正常扫码等待态 |

“无 ACTIVE 不等于无历史”只防错误重建；反向同样成立：有已完成历史不等于存在当前义务。已终结请求的技术 open/迟到终态不能重新变成本次未决；真正尚未得到合法决定的原求值仍是本次责任，不能称为无关历史后换号。原批收口和必要下一意图同事务完成，不等所有历史闭合。

每条真实业务输入到一条原意图的幂等仍然必要，不能删除后声称随机 operation_id 自己能防重。它只保存在该笔业务记录，既不创建线级根，也不串出“谁没有后继谁是当前”的协调链：

| 本次真实输入/条件 | 本次单笔意图与恢复 |
| --- | --- |
| 本次事务未见本作用域原供架请求记录，且无可继续原面、明确 NONE、有合格 FIFO 队首 | 在同一 SERIALIZABLE 推进事务读取该作用域实际求值/执行及 FIFO，再登记新的原 operation_id/消息。队首只记录需求/参数观察，不作为求架幂等键，不生成 FIRST 或队首所属令牌；不改箱行、不固定整批成员 |
| 当前原 WAIT 已消费、到期且仍需供架 | 该条原 WAIT 事实的再次求值动作只登记一次，保存自己的新 operation_id。原 operation_id 是定位这条已知业务事实的引用，不拿它串链或推算当前业务 |
| 本次原 READY 执行按原义务可收口，仍需下一批 | 用该原执行的实际收口事实识别这一次新求架动作，保存独立原请求；不以每次唤醒、收口理由或不同架的回调各登记一笔 |

队首是需求观察和本次登记的输入快照，不是当前请求身份：真实回架、原轮次结束或人工实际移出都可改变队首。请求一经提交，即使 A 已离队、B 成为队首，仍先按原求值/执行及原意图关联恢复；不能因原头不在队列就废弃请求、改参数/operation_id 或替换来源。供架不绑定固定箱集合，后续回箱仍按真实 FIFO；新队首也不能把旧回调改挂成自己的请求。队首尚未就绪/已分配/在途仍先恢复其原义务，不先过滤后另取输入。

**U06 结论：请求级唯一约束不够，删除这项补丁。** 待决行在消费 WAIT/READY 后退出条件唯一索引，旧 Repeatable Read 快照仍可认为没有原请求；两个随机 operation_id 是两条合法消息，Outbox 不会合并它们。RR 下再查一次、只锁未更新的旧行均不构成这项集合判定的串行化证明。已知原经过/动作/请求的恢复仍用原业务键及唯一约束；只有“查询当前集合后，决定登记新的求架请求”需要这项隔离加强，不能从“存在多个查询”推导所有事务都要升级。manual-picking 的 current/decide 行为可复用，但其调用方 WorkLine 锁不是本项目已拥有的保证，也不移植。

<a id="roller-u06-minimal-transaction"></a>
**最小范围是原宿主中会进入 BIN_Roller 架流/正常求架检查的单条独立 advance 事务，首 SQL 前采用 PostgreSQL SERIALIZABLE。** 复用原 session_factory、公开读口、业务唯一性、Outbox/after_commit 和 40001 有界整事务重试。这是在不加手工锁、占位或协调记录前提下，针对本地集合判定的最小方案，不是数据库默认或整业务所有事务升级。若宿主只有一个会调用该检查的统一 advance，就在该入口整笔设置；不为细分 work/分支另造隔离选择器、事务执行器、第二入口或拆开消费与登记。已有且确实不进入架流/求架的纯生产独立入口保持原策略，不能从它旁路登记新 drain。

| 原路径 | 事务与业务职责 |
| --- | --- |
| ECS/WMS receiver、平台结果接收/应用 | 原 session/原隔离保存收据、物理事实、原结果及待办；SCAN2 委托/合法即时释放和供箱需求受理仍按原合同。不消费 drain 的业务求值/READY 执行、不汇总供架批次或登记新 drain；框架保存原响应不等于业务消费 |
| scan_pending 的候选发现 | 原短会话只给原 work/记录 ID 和本轮遍历上界，不升级隔离，不把候选中的无当前/FIFO 副本当作推进许可 |
| 会触发求架的 SCAN、FEED、RETURN_BATCH、RACK_CYCLE、DRAIN 及相关生产推进 | 都经原宿主上述独立 advance；先消费本次原事实，再经唯一架流/正常求架实现读取作用域状态，保存原进度、必要后继与原 Outbox；不能只给 DRAIN 分支设置 SERIALIZABLE |
| 不触及上述判断的既有纯生产路径、其他业务及 Sender | 保持原策略；共享结果读口仍使用调用方 session，Sender 仍只处理已提交的原意图，不加平台隔离开关或新调度器 |

相关判定、登记和消费的覆盖以这张表为准：原 WAIT 到期重问、READY 业务消费/执行建立、原周期接纳后的本批收口与必要下一求值，不能留在 receiver 或另一个较低隔离的求架入口。生产上下文受理后沿原 after_commit 立即唤醒同一 scan_pending，未承接 FIFO 仍是可发现的原待办；正常检查条件已满足就在该次 advance 登记，不为本地交接新增等待状态或等下一轮 DRAIN work。目标宿主尚未交付，B7 须核对实际调用路径，不能把这份设计覆盖表称为代码已覆盖。

事务内必须实际查询同业务/线的组件求值/执行集合（包括空集）、本次 FIFO/接续事实，再登记真实请求与原 Outbox；不能从短扫描/缓存带入“没有当前请求”直接写入。成功提交应与这些参与推进的合法串行执行一致；原身份/消费幂等仍不可少，SERIALIZABLE 不修复串行逻辑错误，也不会在同一事务刷新快照。receiver/上下游新事实可随后提交，沿既有通知继续处理，不把隔离当作“已等齐最新事实”或物理互锁证明。仅使用 session 级连接执行选项，随原 session 关闭/连接归还恢复；不设置引擎/连接池默认或另写连接重置钩子。

**失败按原事务恢复，不增加等待协议。** try 覆盖整个 session.begin 上下文及退出提交；SQL/commit 明确返回 40001，回滚整个尝试、关闭 session 后新会话重读，原基线最多 3 次，耗尽保留原待办并继续其他候选。提交连接中断等非 40001 不纳入这个自动重试分支，也不判定旧事务已回滚；后续仍按原 work 进入上述完整 SERIALIZABLE advance，而非进入“确认旧提交”的特殊恢复流程。

**查不到只是本次快照未见，不能证明从未登记或旧事务已回滚。** 已有持久原请求/意图引用时，只沿原 ID/冻结输入恢复；公开结果暂时 NOT_FOUND/UNAVAILABLE 不授权换号。尚未读到原意图时，也不直接生成新的有效请求：须在同一事务实际重读原业务进度、作用域求值/执行集合及 FIFO/接续，按普通规则判定并尝试登记，直到外层成功提交才成立。原业务键/唯一约束处理同一已知动作，SERIALIZABLE 处理集合判定的并发依赖；不能只查单个 message_id 或不同随机 ID 就宣称无竞争。查询异常不能转换为空集，未提交尝试的 UUID 不构成持久原身份；已提交身份不得重生，原消息的发送/技术重试仍只归原 Sender。

旧事务实际已提交时，新事务恢复原记录；新快照尚未包含它且旧事务随后完成时，两次推进仍须满足同一业务唯一性及 SERIALIZABLE 协议，不能把“旧请求未决/WAIT 未到期/READY 未收口却又首登”作为两个都成功的结果。冲突按原事务机制恢复，不依赖内存保留临时 UUID，也不等旧连接结束。原事务实际回滚时，普通推进可按真实需求提交本步；若原请求已经合法履约结束，确有下一阶段需求才登记下一笔。这里不要求先证明旧事务回滚，不以空查询授予许可，也不增加跨系统提交证明或补偿协议。

[PostgreSQL 事务隔离说明](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-SERIALIZABLE)支持上述串行等价而非最新事实保证；[序列化失败处理](https://www.postgresql.org/docs/current/mvcc-serialization-failure-handling.html)要求连同判定逻辑重试整笔事务，不保证固定某条语句失败或有限尝试一定成功。不把 23505、参数漂移或连接异常一概吞成成功/40001。此处只收口 WES 本地事务，不构成 WMS/RCS/ECS 分布式事务。

B1/B5/B7 用独立 PostgreSQL 复现：旧事务读空→竞争请求登记→原请求消费 WAIT/READY→旧事务首次登记，最终须与合法串行结果一致。未到期 WAIT/未收口 READY 恢复原请求；WAIT 确已到期/原批确已收口且仍有需求，允许真实下一求值，不机械断言历史请求总数为 1。另覆盖 commit 时 40001、旧提交尚未对新快照可见而后完成、已提交但客户端未知、重启丢失临时 UUID、重试耗尽及关闭后连接再用于 receiver/其他业务；只断言持久原身份/消费进度/意图与可恢复性，不建提交确认状态、兜底任务或平台隔离测试框架。设计按此收口；B1～B5 及 B7 测试宿主已执行独立 PostgreSQL 对应交错/commit 重试/连接隔离恢复验证，正式生产宿主事务验收仍未执行。

**上下游职责不扩大。** WES 负责本地请求/动作不因重复处理而重建、原身份及事务进度；WMS 负责库存、可用架/面/槽位和 READY/WAIT/NO_BATCH 决策的真实性与一致性；RCS/ECS/PLC 负责运输/设备动作时序、物理互锁及真实结果。WES 不另维护库存/容量账、跨 Transport 时钟顺序、物理站位锁、迟到释放对象令牌或上下游补偿调度；它们的保证由原责任系统按既有合同承担，不加新协议字段或联调前置。上游数据不合法仍按原合同拒绝/留证，不用数据库隔离假造可用资源或成功完成。

人工移出仍由独立 TODO 剔除本次队列，不在此扩展冻结批次接管或让其成为正常启用前置，也不要求该维护路径参与求架隔离策略。

删除固定 FIRST、来源唯一父链、反向找叶子、源 checkpoint、MAX+1 及批次/求值计数器。来源引用只解释一条具体业务意图，不要求历史连成完整链、不把链完整性当求架或扫码前置。原待决、WAIT、READY 履约是实际业务状态；不能把它们替换成线忙字段，也不能为了避免任何状态而丢掉原请求身份。

本点分隔依据与消息身份也直接保存原引用：原扫码事实存 ctx.digest、原字段、原作用域及 receiver 已有 receipt_id 的定位快照，关联原 arrival；receipt_id 不作经过键/物理 FIFO 序号，不级联依赖收据留存。不同内容以已确认的先前经过引用作边界，同内容在该经过的原本点已应用命令结果后以原 command_code 作边界；命令结果经既有公开读口读取，不要求平台新增 Result 序号/接收时间。首次为固定无前序依据。已提交的分隔依据及每条消息关联保持不变；重启不重新选择“最新”依据覆盖它。

并发唯一登记优先沿现有原生冲突读回模式：命中同一具体业务键且原依据匹配时，读取赢家的原请求/经过，继续保存本条消息关联，不重做委托或重算当前参数，不主动迫使对端重扫码。只有真正的事务失败或当前隔离快照无法读取赢家时，才走原事务回滚/新会话恢复；不能把任意 IntegrityError 当成功。

**受理/恢复边界。** 已提交的原消息/经过/命令关联直接恢复。整笔回滚没有留下那次关联时，原消息沿既有 receiver 重报，按已有原事实和 U02 规则重新受理，不保留未提交 UUID；不能把“找不到原关联”直接当新经过，也不能按当前未收口箱强并旧经过。正常的新技术消息已经有有效本点分隔事实时立即保存新经过并进入原业务接缝，不等旧经过关单、上游 Transport、另一条待办或人工确认。

“关联待核对”不作为这个组件的新状态/队列或正常恢复策略。只有原协议/业务中真实缺失、矛盾的关联或原完成回调不合法时，沿 manual-picking 基线保存证据/业务拒绝/原异常处理；不能为了弥补并发设计尚未验证，给所有新扫码加一个等待补证的中间态。早到完工仍不自动补绑，亦不要求新扫码等它。存储/序列化失败是技术回滚重报，WMS 真实 WAIT 按原业务到期，二者不能伪装为“经过待核对”。

receiver 原消息幂等不提供任意不同消息的点级串行化；本次推进隔离加强不改变 receiver 隔离，源项目的锁也不是本项目已拥有的保证。B2/B7 的真实交错验收须证明等价消息一次委托、A→B→A 为新经过、冲突读回及回滚重报不误归属；证明不足保持 U06 技术验收未通过，不能以新增关联等待、时钟前置、头指针或平台接口冒充解决。这里没有新增业务规则待确认或正常流程启用开关。

任何供架/经过的登记去重都不否定可靠到位：扫码原事实和架的实际位置按原关联保存/更新；已登记其他动作的有效到位不被旧 drain 状态挡住，也不被改挂到某个“唯一未收口”批次。物理事实、原履约和已确认业务关联分别保存，不为清除冲突假造完成或接管旧任务。生产 WAIT 仍由业务沿原求值引用幂等推进；本轮不新增平台幂等、排序、事务或调度接口，既有 U07 适配范围保持。

### 7.2 单次推进的提交边界

下述新会话/SERIALIZABLE 仅针对 §7.1 覆盖表中进入架流/正常求架的原宿主独立 advance；不要求其所有 API/纯生产事务升级。扫码事实、生产委托/合法即时释放仍沿 receiver 原事务，不在 handler 另开会话或中途更改隔离级别。接收并发的新技术消息，按 §7.1 的本点经过业务唯一性去重；不增本点前驱条件更新，不另开 advance 事务替代原受理边界。

1. 原业务用现有 session_factory 新开单条事务，在第一条 SQL 前设 SERIALIZABLE；候选扫描的短会话、ORM 对象和结果副本不带入推进事务，原 work 只是重读定位线索。
2. 以原身份重读业务进度和公开结果；由原结果所属模块幂等保存消费依据。需要随后查询本地进度时，由业务显式 save/flush 保证本事务可见，不能指望公开读口替自己 autoflush，也不另开 session 拼新快照。
3. 同事务进入唯一 rack_flow 实现，登记已选后继引用、首个原 Outbox 意图、后续结果待办及本次原批次汇总；本次原周期已经可读的原 CTU/departure 结果也由该实现幂等处理，不因触发 work 类型不同而等待另一条 RACK_CYCLE 待办。箱批次结果消费仍只在所属模块，不在架流复制消费或递归其他 pending。
4. 需要停止时，必须能从持久记录判断真实等待：原未决请求/命令/Transport，尚待合法业务条件的原 FIFO/经过，或确已结束的服务/周期。输入“已消费”不等于相关履约全部结束；pending 不只筛当前 task_id 或未消费源消息；本地后继未完成或尚待接续的原队列不能因该标记而从 pending 消失。
5. 只有外层 commit 才让这些事实、引用和意图一起可见。平台 API 返回句柄、flush 或 savepoint 释放都不是外层提交；登记/存储异常不得被捕获后当作普通业务拒绝或成功委托，单独提交消费标记；平台内部 savepoint 不授权这类部分提交。异常沿原事务回滚，未提交意图对 Sender 不可见。通知仍只用已有 after_commit，不在模块之间另发消息。

已选原步骤再进入登记方法时先恢复保存的原输入及引用：ECS 读取原 call_key/command_code；WMS 使用原 message_id/operation/operation_id 读结果；Transport 用原 task/client_request/caller。已登记的恢复只交原 Sender 处理，原字节/target 键/期限按各协议已有冻结语义保留；不为 WMS/Transport 增加路由快照能力，不用当前 target 选择、设备绑定、数量或超时重新 send/create。接口参数与原身份漂移时沿原接口拒绝/留证，不吞成成功、不换 ID。

复用[现有业务 advance](../../../app/businesses/coarse_sorting/service.py)包围 session.begin 及外层提交的新 session/有界整事务恢复方式处理 40001（当前基线最多 3 次，每次新 session）；仅 §7.1 相关入口按本专项加强为 SERIALIZABLE，不声称该源码已实现目标宿主。组件不自建重试器。已知逻辑唯一竞争若当前快照无法读到赢家，不能在同一失败事务继续选动作；回滚后经原入口按原键重读，不能用新 ID 绕冲突；不承诺把这类所有错误纳入现有 40001 重试分支。其他完整性/输入漂移错误不一概冒充可重试成功；本轮无法推进则保留原持久待办，由原事件/Beat 再定位，不因一次失败清掉义务。

### 7.3 重复、并发、回滚与重启推演

以下是设计推演与验收要求；B1～B5 及 B7 测试装配已有对应分项验证，正式生产宿主与现场验收仍未完成。校验对象是原步骤/消息身份、冻结输入、消费依据和可恢复性，既有 Sender 自身的合法重试次数不当作“重复创建业务动作”。

| 场景/断点 | 应有结果与后续 |
| --- | --- |
| 同一回调重复、另一次业务唤醒或已完成批次重扫 | 技术原身份先判重，业务按原结果/版本幂等消费；无新合法事实时不多出机会、批次、CTU 或 SCAN2 释放。已选后继仍查原引用，不从旧成功再生一笔 |
| 不同技术身份但本点内容连续相同的扫码并发 | 原接收事务按同一经过业务键登记并保存每条摘要的关联；匹配的唯一冲突先读回赢家，仅事务失败才回滚重读，不各委托一次。没有本点头指针/CAS，原受理不等 Beat |
| 即时任务与 Beat 同时处理同一 work | 都重读原记录；同一业务对象的原消费/意图只提交一份，竞争方回滚后读已提交的原意图，不把“另一个已处理”当作可以丢失本地后继 |
| 不同 work 同时指向同一周期/求架 | FEED/RETURN_BATCH/RACK_CYCLE 或多个 SCAN4 按同一真实业务键登记原动作/批次；首次求架在同作用域 SERIALIZABLE 查询/登记中判定，后续按本次已知 WAIT/执行事实及原进度，不以 FIFO 箱充当协调父节点，也不能只靠不同消息 ID 的 Outbox 幂等 |
| 已写消费标记、已选下一步骤或已取得平台句柄，外层提交前抛错/进程退出 | 本次消费、后继、平台登记和 Outbox 全回滚；原外部事实仍由它自己的已提交记录保留。新事务按原业务键重读再做本步，不出现“已消费但后继丢失”或未提交就发送 |
| savepoint 已释放，外层仍回滚 | 原通知随外层回滚丢弃，不能提前唤醒后伪装业务已提交；平台子登记也不独立留下 |
| 外层已提交，通知丢失或提交后进程退出 | 本次业务关联及原意图已在库；原 Sender/业务 pending 与 5 秒 Beat 恢复，不靠内存游标或设备重扫码。若原请求已送出，仍读/重试该原身份 |
| 外层 commit 明确返回 40001 | try 包含退出提交；本次消费/后继/Outbox 全回滚，新 session 重做整笔，读真实当前再恢复原请求；耗尽仍留原待办。不能仅因内部方法已返回就丢失待办或通知成功 |
| commit 连接中断，无法确认是否已提交 | 不纳入 40001 自动重试，不假定回滚；原 work 进入完整 SERIALIZABLE advance。已见原记录只恢复原 ID；空查询不证明回滚，只有完整业务判定/唯一性/依赖校验及最终提交才能成立一次登记。不建确认状态，不等旧连接或另一个恢复任务 |
| 新事务先查空，原未知提交随后完成；其间又有其他求架或重启 | 原作用域实际查询/进度和业务唯一性仍完整参与，不能按新队首旁路首登；不允许不合法的双成功。冲突回到原机制，重启按持久 work/原引用恢复，不要求恢复未提交 UUID；已履约结束后的合法下一笔与重复首登区分 |
| 相关推进 session 关闭，连接随后由 receiver/其他业务复用 | 既有 SQLAlchemy 连接执行选项随归还恢复原默认，不污染后续隔离；不改共享 factory/engine。复用现有测试装配验证，不新增连接池封装/重置钩子 |
| 重启时原步骤已提交但下游结果未到/不可读 | 保留原 ID/冻结输入及 pending，NOT_FOUND/UNAVAILABLE/ACK 都不证明从未发送或已完成；不改挂最新任务/箱/架，不重建新身份。SCAN2 不重新委托，CTU03 已接纳的周期不重新打开或等待最终位置 |

## 8. FIFO 主流程与人工移出例外

### 9.2 U02：本线本点连续事件规则已确认

**用户已确认。** 判断范围是同一工作线、同一点位的相关事件流：该点扫码及原动作 Result；排除其他点位、其他线、ACK 和心跳。不同消息身份但扫码业务内容相同的事件，之间没有其他有效相关事件则归原经过；有其他有效相关事件则发生新一次进站。

**两层处理。** 完整原消息身份的技术重报仍由既有 receiver 幂等；即使之间有其他事件，旧原消息重报也返回原处理，不开启新经过、不新增或提升本点事实。上述连续规则只处理已通过技术判重的新消息，扫码相同按已定义业务内容判断，不以 timestamp/消息 ID 改变单独认定不同箱流事实。

| 本点事件流 | 经过与动作 |
| --- | --- |
| A(新消息1)→A(新消息2)，业务扫码内容相同 | 同一经过；不重复生产委托/放行，不刷新首次到位/FIFO 顺序 |
| A→B→A(新消息) | 后一次 A 为新经过 |
| A→该点原动作的新有效 Result→A(新消息) | 后一次 A 为新经过；是否许可新动作仍按业务/C07，不能把新经过直接当重试授权 |
| A→其他线/其他点扫码、ACK 或心跳→A | 不打断本点连续关系，仍为原经过 |
| A→其他事件→旧 A 原消息重报 | 技术重报返回原关联，不切回旧经过 |
| 已处理 Result 重报 | 原结果幂等，不作为新的分隔事件 |

**本项目职责。** 持久保存本线本点原扫码事实及消息/经过关联，供重启与收据清理后恢复；从这些事实和原 Result 查询辨别，不维护可抢改的本点头指针/前驱或事件流版本；相关 Result 以已持久/公开的原结果事实为准，不能因 Beat 尚未消费而把其后的扫码错误归为连续重报；不是通道许可、协调版本锁或另一个事件总线。SCAN2 每经过只成功委托一次，真实新经过不继承旧完成/旧释放。SCAN4 首次合法进站进入本点业务 FIFO；连续重报不改顺序，已有轮次 SCAN4 FAILED 后新尝试仍保留该轮首次 FIFO。真正新 SCAN3 按 C07 独立建轮，不等待或自动结束活跃旧履约；SCAN4 新经过仍核对当前轮次和本点原动作，不能靠其他点位事件切分。

**状态与剩余项。** 不再要求另加离开传感、外部 visit_id、物理序号或跨设备时钟证明。不可读原码/朝向如何准入属于 U04/U05 的字段和业务合同；不为不可读事件补预期箱码。B1/B2/B4/B7 验证以上本点序列及隔离，不改变通用 receiver 或历史摘要。
