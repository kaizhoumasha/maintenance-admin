# 工作位进场请求额度与货架现场排队设计

状态：按用户确认的修订方案完成本地实现及软件验收，基线 `caca3c0bef16d6a9eff31ff7628fea0e378a05d3`；未提交、推送或部署。日期：2026-11-03。

## 1. 目标与已确认边界

按旧 `wes_backend` 的配置归属，将进场请求额度统一配置到目标工作位，覆盖五层架、取料架、转运架。额度允许 WES 提前下发货架搬运任务，由 WMS/RCS 安排货架就近排队，依次进入唯一物理作业点。

用户已确认：

- `capacity` 表示同时保有多少个有效进场请求，不表示物理工作位同时容纳多少个架。
- 额度以内应真实登记、提交搬运任务；不能用在 WES 中暂不下发的需求等待代替现场排队。
- 保持现有任务准备时机，不在当前任务生产时提前 prepare 后续任务。转运架先统一支持额度配置，不扩展任务预备机制。
- 所有容量的运行作用域限定在单个任务内。同一分拣工作线保持至多一个 PREPARING/EXECUTING 任务；不同任务不共享余额、排队顺序或进场授权，也不混合建立现场队列。
- 用户后续已授权按修订计划开发及软件验收；保留原工作区未提交内容，不提交、推送或部署。

配置归属工作位，运行计数与排队归属当前任务，两者分开：工作位 capacity 是重复用于各任务的配置上限，不是前后任务共享的运行额度池。当前任务结束后，后继任务按原有准备时机取得自己的授权；旧任务释放的名额不会用于预叫后继任务。旧任务同点尚有未交出的进场/排队/到位责任时，阻止新任务在该点建立进场，不能通过新任务重新计数绕过原责任。

因此，`TRANSFER_RACK.capacity > 1` 不会让单个任务产生多个目标架。当前任务仍只有首版计划指定的一个目标架，所以本期实际最多下发这一架；不能用后续任务的目标架填满余额度。

本设计不增加任务抢占、跨任务共享生产许可、未来目标架推测、额外 WMS operation、RCS 队列管理接口、第二个 Sender、实时物理占用账或新的业务调度器。

## 2. 当前实现与实际缺口

| 层面 | 当前行为 | 本次影响 |
| --- | --- | --- |
| 配置 | `WorkLine.five_rack_request_limit`，`position_bindings` 仅保存角色到编码 | 将额度移到工作位配置，保留现有绑定值结构 |
| 五层架 | `bin_roller/rack_flow.py::entry_available` 按本线 roller pending job 计 CTU01 | 改为公共、按当前任务与目标工作位计算的接纳规则；无任务 drain 不借用任务额度 |
| 取料架 | `ManualRackFlow.reconcile_task` 遇到同角色或同点 pending 作业就限制新架 | 为多个不同架建立各自原作业，额度内提前登记进场 |
| 转运架 | 同点单作业限制，且目标架只来自本任务首版计划 | 去掉将正常排队等同冲突的限制；保留首版唯一授权和任务准备时机 |
| 交出判断 | `evaluate_manual_point` 把其他同点 pending job 计入 `direct_unknown` | 区分正常排队、原架直接执行责任和真实位置冲突，避免队列阻塞队头离场 |
| 公共调度 | RackDispatch 已持有原 job/action、进场结果和离场接纳证据 | 统一接纳检查、顺序和释放；继续使用原事实，不另建额度占用表 |
| 生产许可 | 原 ENTER/ROTATE 的严格成功、确切位置与朝向 | 继续逐架校验，并排除同点多个未交出的到位持有者 |

当前 RackJob 表没有“同点只能有一条 pending”的数据库约束，限制主要位于手工业务逻辑中。因此，不能仅新增配置字段，也不能简单把所有 `pending` 互斥删除。

## 3. 方案比较与推荐

| 方案 | 优点 | 代价与选择 |
| --- | --- | --- |
| WorkLine 增加按工作位编码索引的 JSON 配置 | 少一张表，继续锁 WorkLine 即可串行配置和接纳 | 工作位约束、维护及未来复用较弱；可行但不推荐 |
| 新增最小工作位配置表，复用 RackJob/RackAction 记录运行事实 | 接近旧配置方式，数据库可约束唯一位置与合法额度，三类架统一 | 推荐；新增一张配置表，修改管理读写和迁移 |
| 在 `position_bindings` 中将字符串改成对象，嵌入 capacity | 表面上少一个配置集合 | 会改变现有所有位置读取和冻结快照的值结构，影响面更大，不采用 |

已按修订后的实施计划采用新配置表。配置归属工作位、容量仅限单任务、同线单进行中任务与保持现有任务准备时机是用户已确认的业务决定。

## 4. 配置模型与管理 API

### 4.1 最小模型

新增 `WorkLinePosition`，建议表名 `workline_positions`：

| 字段 | 规则 |
| --- | --- |
| id | 本系统自动主键 |
| work_line_id | 所属 WorkLine，配置外键；历史运行事实不依赖该行级联存在 |
| position_code | 与 `position_bindings` 使用的目标位置编码一致，不能额外造一套 location 映射 |
| capacity | 严格正整数，范围 1～2147483647；显式 null 表示不限制请求数量 |

配置唯一键为 `(work_line_id, position_code)`。同线多个角色如绑定同一目标点，只存在一个配置行；同一任务内共享该点额度，不能按角色、架号或 source_kind 各算一份。运行计数作用域为 `(work_line_id, task_id, position_code)`，不同任务不合并计数、不转移余额。

配置行管理的是接收货架的目标工作位，不为 INLET/OUTLET 建立货架额度。建议为 `PositionSlot` 增加标准库类型声明 `position_type`，明确 `FIVE_RACK/RETURN_RACK/TRANSFER_RACK` 为 `RACK_POSITION`，交接口为 `HANDOFF_POSITION`；业务声明继续不可变、仅使用标准库。正式校验以 catalog 合并后的声明为准，不在管理层硬编码 smt_manual 的角色名。其他业务已声明的架位可以配置，但尚未实现的业务阶段不会因此获得执行能力。

新建架位省略 capacity 时默认为 1。显式 null 与“缺失配置行”严格分开：前者不限额，后者阻止新 ENTER，并暴露配置不完整原因。保留 null 是为了无损承接新系统已有的可空五层架限额，不将既有不限额静默收紧成 1。

### 4.2 工作线聚合读写

沿现有 `/api/v1/work-lines` 管理入口读写 `positions`，沿用 admin、`asset:workline:*`、WorkLine.version 和事务审计，不新增一组独立权限或操作端点。工作位 ID 仅供管理响应，不作为 WMS 业务身份。

示例仅说明结构，取料架和转运架的数值不是现场确认值：

```json
{
  "line_name": "KT16",
  "version": 31,
  "position_bindings": {
    "FIVE_RACK": "KT16",
    "RETURN_RACK": "OUT55",
    "TRANSFER_RACK": "OUT65",
    "INLET": "CNV0301",
    "OUTLET": "CNV0302"
  },
  "positions": [
    {"position_code": "KT16", "capacity": 3},
    {"position_code": "OUT55", "capacity": 2},
    {"position_code": "OUT65", "capacity": 1}
  ]
}
```

更新省略 `positions` 保持原值；提供时是完整配置集合，逐项校验并在同一事务应用。重复编码、非法整数、未知架位、架位与交接口类型冲突返回 422/既有校验错误；旧 version、删除仍被引用的配置或违反在途保护返回 409。明确提交空集合不等于不限额；仍有架位绑定或未结束原责任时不能清空。

只增减 capacity 可以在线执行。降低上限不取消、改号或撤回已登记请求，实际数量可以暂时超过新上限；待有效数量严格小于新上限后才补位。提高上限后由原 pending 入口补位。位置编码修改、解绑、删除和工作线删除，必须拒绝破坏该位置未结束原责任的操作；历史 job/action 保留原编码和冻结资源，不因配置删除重写。旧工作位仍有原作业时，不把它的额度自动转移到新绑定点。

本期工作位按工作线独立管理。若配置预检发现多线将同一现场位置码声明为货架作业点，应阻止自动赋予相互独立的多份额度并报告冲突；多线共享一个物理点的全局队列不属于本次实现范围。现有跨线位置冲突保护继续保留。

## 5. 统一接纳与额度生命周期

### 5.1 计数与登记边界

任务内有效数量取自相同 `work_line_id/task_id/目标工作位` 的原 RackJob/RackAction，累计该任务在该点的所有适用 source_kind，不只统计某一类宿主记录。只有当前进行中任务的真实授权可以新建 ENTER；QUEUED 或其他任务不得因该点存在余量而提前进场。

另行检查原责任隔离：即使其他任务不并入本任务计数，只要该点还存在旧任务或无任务流程未交出的进场/排队/到位责任，就暂停本任务在该点的新接纳。这里是原责任门禁，不是跨任务共享容量。任务表终态不单独证明旧架责任已交出；也不因旧尾部未结清而把旧任务恢复为第二个进行中任务。

现有纯回收 drain 的 job 没有 task_id。本次不为它猜配当前任务、伪造 task_id 或建立无任务的多架额度池，保留现有独立原决定、单架串行与 FIFO/交出规则。任务内多架排队不扩展到无任务 drain；同点未结束 drain 责任也不能被新任务额度绕过。

一个原 job 的 ENTER 与原 Transport 在同一事务登记成功即占 1 个名额，必须在真正网络发送前占入；提交接纳、在途、现场排队、实际到位和本架换面期间均继续占 1。发送器重试、重复输入、同架多个面或多个直接取料成员不增加名额。只登记业务需求或尚未绑定 Transport 的候选不占名额，不能用候选数冒充已下发数。

公共 `RackDispatch.prepare(ENTER)` 及 LOCAL_ONLY 历史动作首次绑定路径必须经过同一接纳检查。业务只提供合法原授权，不能通过另一个 create 调用绕过额度。额度已满时保留原候选及身份，暂不创建外部 Transport；已有合法原 ENTER 重查直接返回原动作，不因上限降低阻止其原发送、结果消费或恢复。

```text
合法需求形成原 job
  → 按工作位额度接纳 ENTER，原 Transport 与占额同事务登记
  → Sender 提交给 WMS/RCS
  → RCS 就近排队
  → 本架原到位成功，逐架开放生产
  → 无可承接需求、可交出时登记原 DEPART
  → 原 DEPART 有效接纳，释放本任务本架名额并推进同任务候选
```

额度内同一分拣任务的多个货架搬运请求真实下发给对端；等待 ENTER Result 的 job 不代表货架已经到位。WES 不生成现场排队点、不猜队列物理位置，也不把 ACK 当作到位。

### 5.2 释放表

| 原事实 | 额度处理 |
| --- | --- |
| ENTER 成功、到位、换面完成 | 保持占额 |
| 发送超时、失联、UNKNOWN、缺结果、位置冲突或仍可更正/继续执行 | 保持占额和原责任 |
| 业务成员撤销或父任务结束 | 本身不释放；未下发候选可以 WITHDRAWN，已下发部分按原事实继续 |
| DEPART 严格匹配原意图，取得有效 202/RECEIVED 或 200/DUPLICATE 接纳证据 | 本架释放一次；复用已有 DEPARTURE_ACK 闭合规则 |
| 原 ENTER 可靠终结，实际不在目标点，且没有其他受管点冲突或未决责任 | 沿原 NOT_ARRIVED 规则释放 |
| 原 ENTER 获严格、确定、无副作用的提交拒绝，公开结果证明无接纳、无未决/冲突执行且责任已闭合 | 可以以提交拒绝依据收口为 NOT_ARRIVED 并释放；不能只看 HTTP 状态或一段 reason 文本 |
| DEPART 被拒绝或无法证明接纳 | 不释放；不能换号创建另一条离场链 |
| DEPART 已有效接纳后又收到原失败/取消/终位回调 | 仅原 Transport 备查，不恢复额度、不重开调度、不自动重搬 |

释放依据保存于原 job/action 的 closure_basis/acceptance_basis，使用公共结果读口；不直接查 ReliableMessage，不加第二套出站重试或单独额度计数器。对确定提交拒绝的收口是需要实施和测试的增量，不能声称现有代码已经覆盖所有此类拒绝。

释放名额只授权同一任务、同一工作位内其他有独立合法依据的候选补位；不用于提前准备或接纳后续任务，也不自动为被拒绝的同一原需求建立新进场身份。原任务已结束后，尚未下发的候选停止新接纳，已下发义务继续按原身份结清。业务是否重新授权仍由原宿主合同决定。

## 6. 排队顺序、同架约束与生产互斥

### 6.1 稳定的接纳顺序

建议 RackJob 增加可空的 `admission_order`。当前任务的完整合法进场授权首次具备时，在 WorkLine 锁内为该任务实际目标工作位分配一次单调顺序，保存到原 job，重试不变。可按该任务该位置历史 MAX+1 分配，建立 `(work_line_id, task_id, point, admission_order)` 的非空唯一索引和扫描索引，限定 task_id/admission_order 均非空，不再另建队列表或配置行计数器。无任务 drain 不取得任务接纳顺序，继续原串行流程。

同一任务同点可接纳候选按该顺序补位。业务将多个需求转换为候选时，保留本任务的 plan_revision、member_order，再交公共登记；不能让分页 ID 或多个 source_kind 的轮询顺序决定插队，也不合并前后任务的候选。原授权有效性变为 UNKNOWN 时，队头保留并暂停该点的新接纳；确定撤销、失效或已闭合候选不再阻挡同任务其他合法候选。

RCS 负责已接纳任务的实际现场队列。WES 的接纳顺序不等于对 RCS 物理先后顺序的观测，不承诺对端不支持的强制抢占或重排。

同一物理架不得在尚未交出责任的原过程之外，再创建同时有效的另一条进场链。该保护覆盖三类架和不同 source_kind，不只查询手工业务自己的 pending 列表。相同工作位的多个不同架是合法排队，不作为同架冲突。

### 6.2 满额候选的关联与补位

候选登记时即固定原 job 关联，实际接纳 ENTER 后再固定准备动作关联：转运架先保存首版计划的 `target_job_id`，待接纳后填入 `target_action_id`；直接取料成员先关联 `rack_work_id`，再关联 `preparation_action_id`。动作尚不存在时，空 action 关联不能被解释为到位或生产许可。

满额后保留的原候选必须能由现有 TASK/job pending 重扫再次进入公共接纳，前提是其原任务仍是当前进行中任务。不能因为成员已经绑定 job 而被 `unbound` 筛选永久跳过，也不能因为 target_job_id 已存在就跳过该转运架后续接纳。同任务名额释放或上调后，不需要新 plan_delta、新任务或换号才能补位；结束任务的候选不得借旧通知重新进场。

同任务、同角色、同点、仍 ACTIVE 的同架后续面复用原 job 和接纳顺序，不再申请 ENTER 或重复占额。RELEASING 的旧过程不吸收后来授权；新出处候选需等同架旧责任闭合后才能接纳。

### 6.3 唯一物理作业点

生产仍必须绑定本 job 的原 ENTER/ROTATE、实际成功结果、精确目标点与面，以及原业务许可。排队架没有到位成功结果时，不能承接投箱、直接取料、箱作业目标许可或换面。

为点位生产授权核对“尚未交出该点责任的到位持有者”：正常排队记录与合法待补位需求不算物理占位；若出现两架在同一工作位均被报告到位、前架又未取得离场接纳，则属于冲突，不能同时授予生产。该判断读取原动作与闭合事实，不引入物理位置缓存或额外占用表。

取料架 `reconcile_task` 要从“每角色只选一个 pending 架”改为“按原成员顺序为不同架形成各自 job，并逐个请求公共接纳”。同架后续面沿原过程关联；正在离场的旧过程不能接收后来授权。

`evaluate_manual_point` 中正常排队的其他架不得使当前架的 DirectHandoff 变成 UNKNOWN，否则会形成“队尾等队头、队头被队尾阻止离场”的循环。仍须保留同架责任、实际位置冲突、未决盘/箱操作、无归属事实和关联错误的阻断。同样检查 BIN_Roller 的生产面选择、回箱机会和交出评估，不把 queue job 当作已到位的可服务架。

### 6.4 转运架范围

保留 `prepare_next` 的同线单个 PREPARING/EXECUTING、首版唯一 target_rack、原队列领取冻结和取消规则。不改任务表执行位唯一索引，不增加“仅准备资源”状态，也不允许为未知后继任务推测架号。

因此，转运架额度仅控制当前单个任务按原时机已经取得授权的请求。当前合同每任务只有一个 target_rack，capacity 即使设为 3，实际也至多使用 1；其余名额闲置，不从后继任务补齐。后继任务成为唯一进行中任务后使用自己的额度，并须先通过该点旧责任隔离检查。本期不改变目标架数量合同。

## 7. 并发、配置更新与恢复

- 新接纳、额度释放、原输入和配置变更均以 WorkLine 锁作为同线串行入口；读取全部关联 RackJob，按现有 ID 顺序加锁。新增配置表不引入反向锁序。
- 持锁后同时重验唯一当前任务、原 job.task_id、任务终态和同点旧责任，不能仅在事务开始前检查一次。额度计数按本任务过滤，旧责任门禁则读取全部原归属；两种查询不得互相替代。
- 推进沿原 SERIALIZABLE 整笔事务与最多三次新会话重试，保持 WorkLine → Devices → RackJobs → 宿主主体 → RackActions 的顺序。公共接纳检查和 Transport 登记原子提交。
- 位置配置修改先锁 WorkLine、核对 version，再写配置与审计；不能与新 ENTER 分别检查、分别提交。
- API/worker 同版运行；丢通知、重复通知、进程重建均由原 `scan_pending` 和 Beat 兜底，重读原 job/action 即可恢复有效数量和稳定顺序。
- capacity 上调或释放名额后使用既有业务通知/待办入口，不新增专用调度任务；即使没有新配置唤醒，原 Beat 也能补位。
- 配置停线阻止新接纳，原发送意图、结果消费、离场接纳和安全收口按已有责任继续；恢复启用只推进原身份。

本次不以 capacity 或 WorkLine 锁证明跨线共享物理点的全局互斥。跨线已知冲突仍按原公开事实保护。

## 8. 迁移与兼容

### 8.1 只迁移本项目配置与运行记录

新 revision 从实施时实际唯一 head 接续，不改已有历史 revision，不导入旧 `wes_backend` 的运行数据。

1. 停写预检现有工作线、有效绑定、同码异类、跨线现场点重复以及原未结束 job 的冻结点位。
2. 建立工作位配置表，为已绑定的各 RACK_POSITION 建立一行；同线同码去重。
3. FIVE_RACK 复制原 `five_rack_request_limit`，包括 null；没有与 FIVE_RACK 同码的取料架和转运架初始设 1，以保留原本逐架推进的效果。同码多个角色只建一行，有唯一 FIVE_RACK 原值时以该值决定整行，不再用其他角色的默认 1 覆盖。大于 1 的新值须由实际配置显式设置。
4. 如存在非空旧限额但无法唯一对应 FIVE_RACK，整体拒绝迁移，不丢掉原值。仅在原冻结资源能证明位置归属时建立未绑定但仍有责任的配置行；不能按当前绑定猜旧目标。
5. 按原 task_id 与工作位分别为已有任务 job 补 admission_order；已有外部请求以可证明的原提交/登记顺序为依据，不能以 UUID 大小补造。不能证明同任务内的多条顺序整体拒绝，不用迁移过程重发任务。无任务 drain 保持空任务归属和空接纳顺序；任务来源缺失或与原证据矛盾时不按当前工作线任务补归属。
6. 不修改原 job/action/Transport/operation/client_request_id、冻结 payload、结果版本、接纳及闭合证据。
7. 完成配置核对后删除 `five_rack_request_limit` 列和管理 API 字段，保持单一配置来源。

旧管理调用端需改为 `positions`；不同时维护两份可写额度。WMS/ECS 的 operation、载荷、模板和 Sender 不因这次额度归属变更而改变。未知旧字段按当前 strict 管理合同拒绝。

### 8.2 降级

只有能无损表达回旧模型时才允许：五层架额度可唯一还原；其他架位 capacity 不能大于 1 或不限额；不能存在旧单作业逻辑无法处理的多架待办、无法表示的新顺序或新闭合依据。所有拒绝须在 DDL 前发生。配置层面可回退不等于可以把已在现场排队的多个货架搬运请求撤回。

## 10. 验收规则（实施后执行，本轮未运行）

| 行为 | 必须证明的结果 |
| --- | --- |
| 配置归属 | 同点别名共享一份配置；运行计数限定任务与工作位；不同任务不共享余额；非法值/缺配置/旧 version/在途删除被拒绝 |
| 提前下发 | 五层架和取料架分别 capacity=3，至少五个有效计划授权时仅前三个真实登记并发送；第四个留在 WES，无外部身份；公共接纳对 TRANSFER 同样使用点位额度，但宿主用例不虚构五个同时活动的任务或同任务多个目标架 |
| 单任务约束 | 同线始终至多一个 PREPARING/EXECUTING；任务 A 尚在进行，即使各点有余额也不为任务 B prepare 或下发进场；任务 A 的释放不推进 B 的候选 |
| 转运架授权范围 | 当前任务只有一个目标架时，capacity=3 也只下发这一架；不跨任务填满；后继成为唯一当前任务后，同点旧责任尚未交出时仍不能进场 |
| 到位前置 | 三个 ENTER 均被接纳时，仅真实到位的确切架能生产；ACK、队列记录和错误架结果不能授予许可 |
| 正常排队 | 队尾 pending 不阻止队头按真实无需求与交出条件离场；多个架的成员、面和生产身份不串用 |
| 释放与补位 | ENTER 成功不释放；DEPART 有效接纳恰好释放一次并补一个原候选；重复/迟到结果不扩额 |
| 非成功 | 严格拒绝且无执行责任、可靠未到场按证明释放；超时、未知、同点取消、冲突、仍可继续执行保持原责任 |
| 同架与多面 | 相同原授权重试不增加 Transport；同架跨类别不能重复进场；换面不重复占额 |
| 并发 | PostgreSQL 双连接在最后一个名额竞争时不超发；管理改额度与接纳交错、提交失败和 40001 重试不丢身份 |
| 容量更新 | 3 降到 1 不取消已有三条；上调后无需新计划即可补位；null 明确不限额但仍遵守生产和冲突门禁 |
| 旧尾部隔离 | 旧任务结果、拒绝、离场 ACK 仅更新旧 job/action 和原依据；不重置新任务计数，不把旧等待架改绑到新任务；同点旧责任的阻断不能被新任务空计数绕过 |
| 普通/drain | 有任务供架只用本任务额度；无任务 drain 保持单架串行、不借当前任务 ID 或余额；两者同点原责任未交出时不混合建立队列，FIFO/原决定仍生效 |
| 恢复 | 重复通知、漏通知、非 eager worker/Beat 和重建均以原身份恢复，等待顺序稳定 |
| 迁移 | 旧 null/正数保真、三个架位默认保守、原在途任务完整保留、顺序矛盾原子拒绝、有损降级 DDL 前拒绝 |

历史模拟材料可复用真实任务/架/面/结果作为样本，但必须保留“历史数据审计”“新系统业务模拟”“真实对端/现场验收”的区别。RCS 就近排队、唯一物理点到位语义和最终安全互锁仍需现场验证，不能由本地并发测试代替。
