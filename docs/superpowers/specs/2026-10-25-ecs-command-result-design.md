## 1. 目标、依据与现状

### 1.1 目标与非目标

目标是让使用本模板的业务项目能够在自己的事务里登记一条 ECS 命令，由唯一的可靠发送器发送，并通过结果回调及公开的命令查询接口观察结果。必须区分命令接纳、回调持久接收、设备报告的物理终态和业务应用结果。

本轮设计不包含 WorkLine、库存扣账、拣料流程、自动取消、自动迁移旧命令、人工强制重发接口、结果纠正协议、未知事件回放、生产设备管理页面和新的重试调度器。WAITING_RESULT 停留时长告警不在本轮：本设计不设结果超时，停留监测与阈值由 P2/消费方按现场 SOP 确定（见 §5.1）。设备状态查询、具体事件、`is_debug` 自动命令及 ECS_TEST 业务规则属于 P2 或消费项目。

## 2. 方案与分层决定

| 方案 | 取舍 | 结论 |
|---|---|---|
| 复用可靠层，增加通用的冻结投递快照、暂停及事务生命周期端口 | 复用事务发件箱、租约、并发与停机协调；需要修改通用层并回归 WMS | **用户已选定的方向** |
| ECS 自建持久派发器，复用单次 HTTP | 可独立定义状态，但重复建设领取、恢复、围栏、清理和停机机制 | 不采用 |
| 每设备/每实例静态多 target，复用现有启动注册 | 无需快照与动态客户端缓存；但设备改址后旧命令会被发到新地址或需重启共享服务，无法满足"免重启改址、旧命令冻结旧地址"（接入指南 89/97 行的动态路由与地址冻结要求） | 不采用（保留原命令地址快照） |

以下内部字段、状态与默认值是已实现的 P1 设计约定，不是供应商 wire 新字段；代码验收不等于供应商已确认。

| 层 | 职责 |
|---|---|
| 消费项目的业务 service | 确定业务调用身份、设备及附录，提供已生效的路由配置；决定如何应用结果 |
| ECS 接入 service / adapter | 命令持久化、地址授权校验、请求冻结、ECS 响应分类、结果关联、业务状态和查询出口 |
| `app/reliable/` | 接受冻结投递快照，唯一调度发送；支持明确的未知处理策略、暂停、租约围栏和注入的事务端口；不认识设备或 ECS 错误码 |
| `app/reliable_runtime.py` 等装配 | 注入设备路由提供者、ECS 生命周期实现、按地址管理的客户端提供者；统一启动关闭 |
| `app/http_client/` | 对已确定地址执行一次请求；不增加设备、数据库、业务或重试依赖 |

不得按协议名在可靠层硬编码 ECS 分支，不让适配器查设备表，不把完整 URL 塞进命令正文，也不维护第二份“每设备一个静态 target”的配置。

## 3. P0-A：协议基线

### 3.1 四接口与本次边界

| 方向 | 方法与路径 | 本设计范围 |
|---|---|---|
| 本项目 → ECS | `POST /api/v1/device/command` | P1 实现 |
| ECS → 本项目 | `POST /api/v1/callback/result` | P1 实现 |
| 本项目 → ECS | `GET /api/v1/device/status`，唯一可选参数 `device_code` | 固定 wire；P2 实现，仅诊断 |
| ECS → 本项目 | `POST /api/v1/callback/event` | 已有机制；具体事件 P2，保持现有语义 |

JSON 使用 UTF-8，单条消息最多 256 KiB。复用 strict JSON、请求体限额、错误路径与脱敏工具；拒绝重复键、非有限数等不合规输入。核心类型严格校验，整数排除布尔值。对端时间均为 Unix 毫秒，只作合同内容，不作为恢复顺序权威。

### 3.2 命令内容与身份

命令顶层闭集为 `device_code`、`command_code`、`task_type`、`priority`、`timeout`、`timestamp`、`params`：

- `device_code`、`command_code`、`task_type` 是非空字符串；`priority` 固定整数 `1`。
- `timeout` 为设备动作期望完成时间，不是 HTTP 超时，也不是重试窗口；值域按设备/动作类型随附录版本一并确认（白皮书附录只定义 `params`/`data` 二级字段，不定义顶层 `timeout` 的取值规则）。`timestamp` 为首次建命令的非负 int64 毫秒值。
- `params` 必须是对象；二级字段由确认的设备附录定义。没有附录不创建正式命令，不同时发送顶层 `source`/`params` 两套结构。
- wire 的全局命令身份为 `command_code`；本方新命令使用现有 UUIDv7 生成器，保存后不再生成。结果查找原命令后必须再次核对 `device_code`，不能凭设备或时间猜关联。
- 消费方提供独立的业务调用键（业务域、调用身份）。数据库唯一约束保证同一调用只创建一条命令；同业务调用键、同业务输入返回旧命令，不重新选址。输入不同报本地冲突，不创建第二个物理动作。
- 首次保存完整请求字节、原始时间、设备、动作类型、附录版本、路由身份和地址。技术重试严格复用这些内容；不启用“时间戳变化也视为等价”的比较器。

旧指南中的 `(device_code, command_code)` 可作为本方关联校验，但不能允许同一全局 `command_code` 在另一设备上重新创建。业务调用键与 wire 命令身份各自保留，不能互相替代。

### 3.3 命令响应分类矩阵

分类必须基于完整 HTTP 响应、JSON 对象、严格整数 `code`、字符串 `message` 和已知可选字段类型。设计采用 `code` 与 HTTP 状态相等的规则；非 200 分支的这一约束在[实际接入](../../integrations/ecs-acceptance-checklist.md)时须与供应商核验。`trace_id` 出现时必须是非 null 字符串；未知顶层字段忽略，不参与分类。JSON 媒体类型允许带合法字符集参数。

| 条件 | 接纳判断 | 本方处理 |
|---|---|---|
| HTTP 200，JSON，`code=200`，`message=ACK` | 已接纳 | 投递 DONE；命令等待结果，不再提交 |
| 400 / `INVALID_ENVELOPE` | 明确未接纳，载荷错误 | 停止，命令 REJECTED |
| 404 / `DEVICE_NOT_FOUND` | 明确未接纳 | 停止，命令 REJECTED |
| 405 / `METHOD_NOT_ALLOWED` | 明确未接纳 | 停止，命令 REJECTED |
| 413 / `PAYLOAD_TOO_LARGE` | 明确未接纳 | 停止，命令 REJECTED |
| 422 / `ANNEX_VALIDATION_FAILED` | 明确未接纳 | 停止，命令 REJECTED |
| 409 / `IDEMPOTENCY_CONFLICT` | 接纳事实不确定且发生身份冲突 | 投递 HELD（原因 `IDENTITY_CONFLICT`，见 §5.1 闭集）；命令 RECONCILING，禁止自动重放 |
| 429 / `CAPACITY_EXCEEDED` 且 `Retry-After` 有效 | 明确未接纳 | 原身份延后重提，且不早于对端要求的时间 |
| 429 缺失或带无效 `Retry-After` | 不满足自动重提条件 | HELD，记录合同不合规，待对账 |
| 503 / `TEMPORARILY_UNAVAILABLE` | 明确未接纳 | 原身份、原地址、原字节退避重提 |
| 500/502/504 / `TEMPORARILY_UNAVAILABLE` | 交付未知 | HELD，待对账 |
| HTTP 客户端证明 NOT_SENT | 本次请求未发出 | 原身份退避重提；不能抹去此前的未知事实 |
| 写入/读取超时、响应不完整、超限、非法 JSON、类型错误、未知状态组合等 | 无法证明未接纳 | HELD，待对账 |

`Retry-After` 的处理规则：支持非负整数秒，以及可解析的 HTTP 日期；日期需为未来时刻。重复且有歧义、负数、小数、溢出或无法解析均无效。转换成持久的最早重提时刻，再与本地退避取较晚值。不得沿用现有通用策略的截短上限而提前重发；超过本地允许等待范围则暂停，超过发送截止时间则不再新发。具体解析实现沿用已有工具或标准库，由实施计划确定。

当前新命令统一采用项目批准的W=300秒，正式与调试路由共用PROTOCOL_RETRY_WINDOW，创建时精确校验并冻结；不由请求或部署另配窗口，也不借用Transport的一小时TTL。旧调用重入及存量命令保持原冻结期限。对端最低合同D为持久确定终态后至少24小时，活动/未决去重依据不按TTL清理并跨重启保留；真实接入验收核实实际供应商符合性，本方批准/隔离测试不替代真实保证。窗口内明确未接纳的退避复用既有算法，不新增次数预算；UNKNOWN/HELD不因期限或重启解封。

### 3.4 结果回调与错误协议

结果核心字段为 `command_code`、`device_code`、`result`、`finish_time`、可选 `data`、条件字段 `error_detail`：

- `result` 仅 `SUCCESS`/`FAILED`；`finish_time` 为非负 int64 毫秒值。
- `data` 缺省为 `{}`，显式 null 不合法；业务字段按原命令冻结的设备附录解释。
- SUCCESS 的 `error_detail` 缺省或 null；FAILED 必须提供仅含 `code`、`msg` 的对象，值为字符串并按附录校验。
- 顶层 `trace_id`、`event_id`、`causation_id` 等扩展只作诊断，允许 null，不参与去重或权威排序。
- 成功持久接收后回 `200 {code:200,message:ACK}`。非法包络回 400 和脱敏 `error_detail.issues[]`；未知命令回 `404 COMMAND_NOT_FOUND`；内容冲突回 `409 IDEMPOTENCY_CONFLICT`；未开始派发回 `409 RESULT_BEFORE_DISPATCH`；超限 413；事务失败 503。
- `issues[]` 复用 ECS 事件的路径规则，补足结果闭集错误的 `EXTRA_FORBIDDEN`；未知键用 `error_detail.<extra>`，不能回显客户端字段值或字段名。

不增加取消接口、`result_revision` 或供应商私有路径。不同结果分别保留，`finish_time`、摘要和到达顺序均不赋予覆盖权。

## 4. P0-B：动态寻址与客户端管理

### 4.1 设备路由的最小接缝

ECS service 通过注入的设备路由提供者，在调用方事务中取得一个已生效、可发送的配置快照：设备编码、规范化 origin、配置版本/身份、允许的动作及附录版本。它来自受控的设备配置，不接受调用请求传入任意 URL。

模板不新增 WorkLine/binding 业务模型。P1 定义并测试提供者契约，生产实现由消费项目对接自己的设备目录及配置生效机制；缺省实现拒绝解析，禁止悄悄退回固定地址。提供者对读取与配置生效使用锁或版本校验，保证返回的是一个一致快照。测试提供者只在隔离测试或 local 使用。

同一提供者支持发送前校验**当前配置是否仍允许原命令发送**，返回获准、已撤销或无法确认，不重新选择地址。2026-10-27正式目录修订：改址、删除/重登记、换绑及相关管理版本变化使旧命令停止后续发送，不维护历史授权清单。复用RouteSnapshot.version作为提供者拥有的不透明修订标记，及既有设备/工作线版本；具体合同见设备、工作线SPEC§10。配置修改与发送门禁通过一致锁序串行化：修改先提交则本次不得发送；门禁先提交则该次视为在途，之后修改不能撤回它，但下一次尝试必须拒绝。无需扫描改写旧命令快照或新增撤销调度器。

创建顺序固定为：**按业务调用键查旧命令 → 有则核对业务输入并返回 → 无则解析并验证路由/附录 → 同事务保存命令与可靠消息**。并发唯一键竞争失败者读取获胜记录，核对输入后返回，不覆盖其地址和字节。

规范化与授权规则：仅 HTTP/HTTPS 的 scheme、host、port；禁止用户信息、路径前缀、查询和片段，允许输入末尾一个根 `/` 后规范化去除。主机名小写、默认端口等价，设备编码保持原大小写。复用 HTTP 客户端校验；网络范围、设备归属和修改权限由受控配置边界落实，不让可靠层承担设备授权。

### 4.2 持久快照与配置变更

可靠消息增加可空的 `delivery_snapshot`，语义为首次入队时冻结的 origin、协议及未知处理策略；ECS 命令保留同一份投递依据供关联和审计。二者同事务生成并校验一致，不在恢复时重新解析设备地址。

快照是投递身份的一部分：可靠层同 `(target, operation, operation_id)` 重入时，必须比较原始字节和规范化快照；任一不同即冲突，不允许“正文相同就接受地址 B”。正常业务重复入口直接带回旧命令的原快照，不把设备当前配置当作新草稿传入。消息上的协议和 HOLD 策略优先于当前 target 配置；发送、异常处理、租约恢复、停机释放和到期检查都使用同一解析规则。缺失配置不能使快照消息退回 STATIC/RETRY。STATIC 与 SNAPSHOT 模式不允许在同一逻辑 target 存续期相互改用；应以独立目标名区分，新模式不得重新解释旧行。

当前 target 的协议/地址模式若与消息冻结身份不匹配，按配置漂移暂停，不借用新协议的适配器或客户端发送。HTTP 资源参数可以按部署容量调整，但不得改动原 origin、正文、协议或 HOLD 语义。

启动配置增加显式的 SNAPSHOT 地址模式：该逻辑 target 只定义协议、HTTP 资源参数和发送策略，不需要填写假 base_url；逐消息必须有合法快照。原 target 默认 STATIC，继续要求合法 base_url。原数据的快照为空，完整保留既有静态行为。未知处理策略在 ECS 消息上冻结为 HOLD，不能因重启配置变为 RETRY。

| 场景 | 行为 |
|---|---|
| 有效配置 A，创建命令 X | X 冻结 A |
| 设备主数据改为 B，但消费方新配置尚未生效 | 新命令仍按有效配置 A；若配置已被撤销则拒绝新建 |
| 配置 B 生效后创建 Y | Y冻结B；X仅保留原A快照用于查询/结果关联，重复入口不恢复发送，不改投B |
| A 不可达 | X 保持原身份和 A；按未发送/未知分类处理，不改投 B |
| 原配置改址/删除/换绑或管理版本变化 | X后续门禁拒绝并复用HELD / AUTHORIZATION_REVOKED；不改地址、不推断设备取消，原Result仍按证据规则接收 |
| 配置A变更后再恢复原值 | 管理版本不回退，X不恢复发送；新独立有效意图创建新命令 |
| target 缺失、协议不再可服务或快照损坏 | 不发送，不回退到其它目标；快照维护扫描在生命周期端口可用时同事务暂停并暴露错误，不依赖它出现在可领取目标集合中；端口缺失时按 §5.2 安全降级 |

命令存续期间不允许修改其快照、协议或地址来迁移。P1 不提供自动迁移功能。

### 4.3 客户端生命周期

客户端提供者位于应用装配层，通过注入端口供 Sender 使用。缓存键为规范化 origin 加实际 HTTP 资源配置；同地址、同配置的多设备共享客户端，不按设备或命令建连接池。

设计暂定每进程最多缓存 64 个动态客户端（部署容量参数，非协议字段）：按需创建，同键并发只创建一个；满额时只淘汰无在途借用的最久未使用项，先完成关闭再创建替代；所有项在用时不发网，按本地未发送退避等待，不能突破上限或无限挂起领取租约。创建失败不留半成品；关闭期间拒绝新借用，先协调在途任务再关闭全部客户端，取消路径也必须清理。

64 的上限包括正在创建、被借用及正在关闭的动态客户端，创建预留名额与登记必须原子完成，关闭失败不释放名额以继续创建。单次淘汰关闭有界，超时停止该次创建并告警，不让永久不返回的 `aclose` 占满发送任务。先有界取得客户端，再进入数据库发送门禁；不得持有命令/消息行锁等待连接池创建、HTTP 或客户端关闭。该缓存不接管现有静态客户端，资源用量分别可核对。

新租约仍由既有 Sender 的全局并发预算限制；客户端缓存不启动调度器、不自行重试，不跨事件循环共享。没有预热和定时刷新，设备改址无需通过重启更新静态列表。

命令服务不以同设备的历史失败或未终态命令阻止一条有有效业务意图的新独立命令；只验证本次身份、有效路由、静态能力和参数。物理排队、容量和互斥由 ECS 接纳时裁决。暂停只约束原命令，不能成为设备永久封锁。

## 5. P0-C：未知交付、持久暂停与围栏

### 5.1 通用能力增量

增加协议无关的未知处理策略 `RETRY`/`HOLD`：原静态目标缺省 RETRY，ECS 冻结 HOLD。协议适配器仍只分类完整响应；409 冲突返回明确的暂停判定而不是假装为已拒绝，底座只执行该通用判定。

新增可靠消息状态 **HELD** 和暂停原因。HELD 不参加领取、自动重排、普通 `resume`、待发送 TTL 清理或终态保留期删除；没有 `next_attempt_at`。它不是物理终态。需要相应迁移状态/时间约束，不能把 HELD 混进现有 STALLED 预算语义。保持 `delivery_uncertain` 的事实含义，配置错误类暂停不能伪造交付未知。

暂停原因为九值闭集（值名属 §2 所述内部提案；可靠层只存协议无关原因串，闭集定义与解释归 ECS 侧）：

| 原因值 | 触发 |
|---|---|
| `DELIVERY_UNKNOWN` | 门禁提交后无法证明未接纳/未发出的异常（§3.3 未知行、§5.1 执行阶段判定） |
| `LEASE_INTERRUPTED` | 租约超时、发送中进程崩溃、停机取消（§5.1） |
| `CONTRACT_NON_COMPLIANT` | 对端应答违反重提合同，如 429 缺失/无效 `Retry-After`（§3.3） |
| `CONFIG_DRIFT` | 当前 target 协议/地址模式与冻结身份不匹配（§4.2） |
| `AUTHORIZATION_REVOKED` | 原冻结路由被显式撤销，或正式目录配置/绑定/管理版本已失效（2026-10-27修订，§4.2） |
| `PRE_GATE_VALIDATION` | 发送门禁前可证明未发网的配置/校验失败（§5.1） |
| `ASSEMBLY_UNAVAILABLE` | 生命周期端口/必需装配缺失或持续失败（§5.2 安全降级） |
| `EARLY_RESULT_LOCK` | 提前结果封锁并暂停消息（§5.3） |
| `IDENTITY_CONFLICT` | 命令响应 409/IDEMPOTENCY_CONFLICT：接纳事实不确定且身份冲突（§3.3）；命令同时标记矛盾封锁，匹配 Result 只留证据、不自动 settle |

通过公共事务命令支持暂停：在调用方事务中把可发送消息置 HELD，清空租约并保存原因。匹配且可应用的结果可用 `settle` 将 HELD 结束为 DONE；不生成 ACK 响应原文。普通 `resume` 仍只处理原有 STALLED，不解除 HELD。人工对账重发入口不在 P1，查询和日志必须明确显示这一限制。

| 触发 | ECS 的持久处理 |
|---|---|
| 一次交付无法证明未发出/未接纳 | HELD，命令 RECONCILING，保留原始请求和可得响应 |
| 租约超时、发送中进程崩溃、停机取消 | HELD；保守认为可能已发出，不通过重启恢复发送 |
| 完整合法 ACK | DONE，命令 WAITING_RESULT；停止提交，等待 Result |
| 已接纳后迟迟无结果 | 命令仍等待；本设计不设结果超时，停留监测与告警由 P2/消费方按现场 SOP 承担（§1.1 非目标）；不重新创建或提交命令 |
| 明确拒绝 | 投递 FAILED，命令 REJECTED；不等同物理失败 |
| 发送窗口到期，且历次均明确未接纳/未发送 | EXPIRED，停止新发；不产生物理失败结果 |
| 请求仍在途时发送窗口到期 | 保持 SENDING 等待本次有界 HTTP 结束；迟到的合法 ACK/Result 仍可收敛。明确未接纳则 EXPIRED，未知或租约中断则 HELD；不因 TTL 取消在途动作或丢弃响应 |

ECS 的异常处理按执行阶段判断，不沿用“任意本地异常均 FAILED/LOCAL_ERROR”的通用兜底：发送门禁前可证明未调用 HTTP 的配置/校验错误暂停并保留未发送事实；门禁提交后若缺少可验证的 NOT_SENT/明确未接纳依据，包括客户端抛异常、适配器分类抛异常、返回类型不合法、成功响应处理失败，都按可能已交付 HELD。完整响应能保留则保留，但异常本身不能证明未接纳。WMS 的既有异常映射不因此改动。

### 5.2 命令与可靠记录的一致性

ECS 不能依靠定时扫描可靠表来获得业务状态。注入最小的事务生命周期端口：发送前登记，以及发送结果、租约恢复/释放、普通待发送到期、暂停/结算的状态应用；端口只写当前数据库，不发 HTTP、不提交事务。可靠层不导入 ECS 模型，不新增业务结果查询 API。尤其 `expire_pending` 不能只改可靠消息，否则从未领取或退避中的命令会永久停在 QUEUED。

旧静态目标不要求实现该端口，保持无业务投影的原行为。ECS 的 SNAPSHOT/HOLD 目标须同时完成路由、客户端、协议适配器和生命周期端口装配，缺任一项不能启用发送，不能发送后才发现命令状态无人更新。

维护/暂停所需的领域端口必须能由消息冻结的协议身份找到，不依赖该逻辑 target 仍存在。若端口代码或必需命令数据本身缺失/持续失败，无法保证两表同事务暂停，则保持原持久状态、不发送、不单改可靠行，暴露“ECS 装配/投影不可用”并持续告警；不得谎报已持久 HELD 或承诺自动恢复成功。它是可见的安全降级，健康的 WMS 目标继续服务。修复装配后重新维护原记录，仍不因重启直接重发已可能交付的命令。

发送开始前须提交命令上的 `dispatch_started_at`：它表示“从此可能已发出”，不是已接纳或已证明字节离开。登记时必须同时核对当前租约及命令仍允许派发。网络请求在该事务提交后才允许开始；登记失败不发网。门禁须同时持久登记当前租约对应的发送尝试：在明确 NOT_SENT/未接纳依据提交前，该次尝试保持“可能交付”；明确结论只排除本次尝试，不能抹去历史未知。后续重试通过新门禁时建立新尝试，不能沿用上次明确未接纳结论否定新的在途尝试。历史 `dispatch_started_at` 只用于追溯，不能单独授权结果应用。

发送门禁取锁后重新读取当前时间，要求消息仍 SENDING、lease_id 匹配且 lease_until 尚未到期、发送窗口未截止、路由仍获准；不能拿领取时的时间或仅有 token 相等来证明租约有效。客户端获取和锁等待均消耗初始租约，过期租约不得复活。有效门禁可在同事务把租约续至“当前时刻 + 本次 HTTP 总超时 + 原有余量”；提交后、调用 HTTP 前再次检查命令发送窗口及本次租约期限，两者任何一个已截止都不发起请求，进程在门禁后暂停过久时不得迟发。该最终时间检查与 HTTP 调用之间不再插入异步准备工作；仍保留 §5.3 所述无法原子化数据库提交和发网的边界。续租与这些检查只用于有 ECS 生命周期的快照路径，不改变原 WMS 的租约行为。

`finish`、未知暂停、租约恢复/释放、普通到期与相应命令状态投影在同一事务落库。端口失败时全部回滚，保留可再次维护的原状态，不能出现可靠记录 DONE/EXPIRED 而命令永久停留在未派发状态。端口恢复可用后，遗留 SENDING 按 HOLD 收敛，不重新发网。所有回写都先核验消息状态和 lease_id，更新成功后才应用相应命令投影；陈旧发送结果不仅不能覆盖可靠消息，也不能先行覆盖命令终态。

统一锁顺序：**命令 → 配置授权（仅发送前需要）→ 可靠消息**。正式目录配置授权内部按“工作线ID→设备ID”升序取锁并刷新复核；配置管理不反向锁旧命令或可靠消息。领取可仅锁可靠消息后提交，不得在该事务中再等命令锁。发送前、finish、恢复及回调需要两者时先经注入端口锁命令，再锁并复核可靠消息；恢复扫描只筛候选，实际更新按此顺序复核租约。回调收据竞争在命令锁后，未知命令不创建成功占位。不得先批量锁消息再调用领域端口。

快照维护采用每条候选独立的有界事务，命令锁一律不等待（NOWAIT，冲突即跳过该条）——不采用逐条最长 5 秒的锁等待：维护批量默认 100，逐条等待最坏可占住共享 Sender 数百秒并阻塞健康目标的领取。快照恢复与到期维护共享一个从候选扫描前开始的单调时钟整轮 deadline，预算复用 `ReliableConfig.poll_interval_s`（当前默认 1 秒），不为两类维护重置预算、不新增环境参数。扫描、连接获取、端口调用、SQL、提交和失败后的取消/回滚均纳入，并预留清理时间。单条执行上限不得超过剩余预算与现有 `db_pool_timeout_s` 的较小值；耗尽不再开始新候选，完成有界清理后让出领取机会，剩余候选由游标下轮继续；锁冲突/端口异常仅回滚该条并记录，不中断健康目标的维护与发送。扫描用游标推进到本轮后续候选，结束后再回绕，防止最老的一批失败记录占满每次 LIMIT。扫描候选不按当前 target 配置丢弃快照消息；未配置的旧 STATIC 消息仍按现有规则保留 PENDING。这个分流也适用于过期扫描，不能把 ECS 投影失败传播为整次 `Sender.tick` 失败。

NOWAIT 只约束行锁，不能替代表锁、连接获取或端口等待的 deadline。取得连接后、首次业务锁前设置事务局部 `lock_timeout`、`statement_timeout`，不超过该条剩余预算；不足以设置正数超时或启动并清理下一条时结束本轮，不能将 0 当作立即超时（PostgreSQL 中 0 表示禁用超时）。端口须响应取消，不得在后台继续持锁；取消后须确认回滚，连接状态不明时隔离告警、不得复用。数据库整体不可用只报告故障，不能宣称健康目标仍可领取。

Result、正常发送门禁与 finish 须在首次命令锁之前设置既有 5 秒的事务局部锁/语句超时上限，连接获取仍受现有连接池上限约束；不能等到插入回调收据时才设置。维护事务使用前述更短的剩余预算。这些局部限制只用于新增 ECS 路径，不改变旧 WMS 事务及重试规则。

锁语义依据：[PostgreSQL 17 行锁与事务规则](https://www.postgresql.org/docs/17/explicit-locking.html)；连接池复用及关闭依据：[HTTPX 异步客户端](https://www.python-httpx.org/async/)与[资源限制](https://www.python-httpx.org/advanced/resource-limits/)。这些资料用于核对机制，不替代项目现有实现和本节的业务约束。

### 5.3 发送与结果到达的竞态

提前结果的判定点是**回调取得命令锁后读到的已提交状态**，不是 HTTP 到达时刻。发送门禁先持锁并提交时，等待该锁的回调随后按已开始派发处理；回调先取得锁且没有开始标记时，它先封锁命令，发送门禁随后必须失败。P1 不引入按网络到达顺序排序的额外机制。

| 结果到达时 | 处理 |
|---|---|
| 未知 `command_code`，或设备与原命令不匹配 | 404，不应用；不补造命令或关联其它设备 |
| 回调先取得命令锁，读到尚无 `dispatch_started_at`，包括消息已领取但门禁尚未登记 | 持久保存该次 409 `RESULT_BEFORE_DISPATCH`；封锁命令，暂停消息并撤销租约。后续相同结果仍回同一错误 |
| 当前尝试已通过门禁且尚未被明确未发送/未接纳结论排除，或历史存在交付未知，或已有合法 ACK；命令未被封锁 | 可以接收匹配结果并结束发送义务；包括首次和后续重试仍在途、ACK 尚未落库的情况。当前尝试只表示可能交付，不证明已发出；仅历史派发标记不构成该依据 |
| 已 HELD，原因仅为交付未知/租约中断，原命令及结果匹配 | 合法 Result 可解决原命令未知结果并 settle；不重新发送 |
| 因正式目录配置变化停止后续发送，HELD / AUTHORIZATION_REVOKED；原命令未封锁且有可能交付或ACK证据 | 2026-10-27修订：合法迟到Result仍使用原command_code/device_code/附录接收并结算；不要求当前设备/角色授权，不重新发送，也不自动推进新角色业务；适配现有result.py的HELD原因判断，不放宽其他封锁规则 |
| 原命令明确 REJECTED，或历次均明确未接纳/未发送且没有新的可能交付尝试（无论是否已 EXPIRED，含仍在退避重提的 QUEUED），随后收到 Result | 保存矛盾证据并返回 409 `IDEMPOTENCY_CONFLICT`；命令进入 RECONCILING 并标记矛盾封锁，保留原拒绝/到期/退避依据。原可靠消息 FAILED/EXPIRED 不改写为 DONE，不自动应用设备终态 |
| 已因提前结果、身份冲突、明确拒绝后的矛盾等封锁 | 后续结果只留证据或返回冲突，不自动解除封锁、不驱动物理动作 |
| 相同结果已处理 | 返回首次 ACK，不重复应用；迟到发送回写失去围栏，但该次响应原文仍作为迟到证据持久保存——不改终态、不重发、不生成新的发送义务；明确拒绝与已应用 SUCCESS 同存时标记 `needs_reconciliation` |

互相矛盾的发送应答与 Result 也按锁后提交顺序处理：明确拒绝先提交，之后 Result 走矛盾 409；合法 Result 先提交则保持原已应用终态，随后发送应答不得将它改回 REJECTED/WAITING_RESULT，失效租约的回写不产生业务投影，但该次应答原文按上表作为迟到证据旁路保存。不同核心 Result 到达已确定终态时，原 SUCCEEDED/FAILED 不退回 RECONCILING，另记 `needs_reconciliation` 和冲突证据；消费方已完成的业务不自动撤销。Result 可应用的前提是命令未被封锁，且存在至少一项持久依据：当前尝试已通过门禁、尚未被明确未发送/未接纳结论排除；历史存在交付未知；已收到合法 ACK。仅已领取或历史派发标记不构成该依据。历次均明确未接纳/未发出且没有新可能交付尝试的命令收到匹配 Result 一律按矛盾处理，判定不随重试窗口是否恰好过期而翻转。Result 先应用后迟到 NOT_SENT/未接纳结论同样保存为矛盾证据并标记 `needs_reconciliation`，不回退已应用终态。这里的提交顺序只决定哪份结论被应用，不意味着其物理事实更权威；证据矛盾仍需核对。

先落库的暂停不能撤销已经发生的网络或物理动作。发送前登记之后、真正发网之前仍存在不可消除的小窗口；崩溃时宁可待对账，不能把本地标志解释成“肯定已发出”或“肯定未发出”。

### 5.4 WMS 兼容性约束

通用扩展不能把 ECS 的严格规则全局化。下列行为须由实施前后的同一组 WMS 测试验证，并增加混合目标测试，而非仅检查新 ECS 分类器。

| 接缝 | 原有 STATIC/WMS 行为 | ECS 快照路径 |
|---|---|---|
| 配置/公开类型 | 保留 `TargetConfig(name, base_url, protocol)` 等现有调用；新增字段有兼容默认值，静态地址仍必填 | SNAPSHOT 解析出有效 HTTP 配置后才交给校验器；不传空或假地址绕过旧校验 |
| runtime 可服务集合 | 现有静态客户端仍按 target 启动创建；未配置或漏适配器的目标按原约定跳过/告警，空配置仍可维护历史记录 | 能服务性依据配置、冻结协议和已装配客户端提供者，不要求提前存在每个 origin 的客户端实例 |
| 重试/响应提示 | UNKNOWN 继续原排期；固定间隔、随机退避、Retry-After 上限保持原规则 | HOLD 与“不截短对端等待”只作用于快照路径，不修改 WMS 的全局计算规则 |
| 生命周期/恢复 | 无端口的旧消息不锁 ECS 命令，不增加其事务副作用；保留原租约、STALLED/resume、TTL 和终态清理 | 所有领域投影按 §5.2 进行；单条失败独立，不阻断旧路径 |
| 结算 | `Outbox({}, {}).settle` 仍可按存储身份结算旧消息，不要求目标配置或 ECS 端口；Transport 的“收到回调即结束提交”保持 | ECS service 完成身份/状态判断后才结算；HELD 可结算但不能用普通 resume 解封 |
| 本地异常 | 保留既有 FAILED/LOCAL_ERROR 映射及证据规则 | 按执行阶段和是否可能已交付判断，不用 WMS 兜底覆盖未知 |

上述隔离仍复用一个 Sender 和已有总并发预算，不新增独立重试器。共享容量不承诺 WMS 专用吞吐，但一条 ECS 错误不能永久停住健康 WMS 消息。

## 6. P1 命令与结果闭环的具体交付

### 6.1 数据与服务边界

新增 ECS 命令记录，至少包含业务调用键及输入依据、全局唯一 command_code、设备/动作/附录、冻结请求和投递依据、发送窗口、dispatch_started_at、各租约尝试的门禁及明确未发送/未接纳/未知依据、接纳或拒绝/到期依据、命令状态、原始结果及封锁原因。正式命令与可靠消息必须在同一数据库事务创建；回滚不留下可发送记录。

命令状态为 QUEUED、DISPATCHING、WAITING_RESULT、REJECTED、RECONCILING、SUCCEEDED、FAILED、EXPIRED。FAILED 只表示已接受的 ECS FAILED 结果；本地错误、投递过期、拒绝和未知均另记，不能混用。保存是否实际收到 ACK 及可得原文；Result 先到不伪造 ACK。

领取消息本身不改命令为已派发；发送门禁成功才进入 DISPATCHING。NOT_SENT/合法 503/合法 429 若仍允许重提，则命令回 QUEUED 并保存本次未接纳依据；合法 ACK 才进入 WAITING_RESULT。已有应用结果和封锁状态不能被这些普通投影降级。命令为 RECONCILING 时必须同时给出具体原因，区分交付未知与从未发送的配置暂停。

结果证据单独持久保存：以规范化的 command_code、device_code、result、finish_time、data（缺省 `{}`）、error_detail（SUCCESS 缺省归一为 null）计算消息摘要；扩展字段不参与。相同消息重报复用原响应；同一命令的不同核心结果分别保存，只有首个符合关联及状态规则的结果可应用，其余按冲突处理，绝不按“最后到达”替换。

复用 `callback_receipt` 的插入、查询和响应保存能力；结果命名空间为 `ecs.result`，operation_id 放 64 位消息摘要，不使用 command_code 作收据身份——原因不是列长度（现有收据列为 String(64)，36 字符的 UUID 本放得下），而是同一命令可先后到达多条不同核心结果（§5.3 冲突路径），按 command_code 建收据会让第二条结果占不到身份；内容摘要使每条结果各占一行收据，冲突由命令/证据约束处理。命令关联和一个结果只应用一次由命令/证据的持久唯一约束保证，不能依赖 90 天后会清理的收据。相同规范化内容由命令和证据复核，摘要不是业务身份。

接收顺序为限额及核心包络校验 → 查找并锁原命令 → 查持久结果证据/首次响应 → 新消息才按原附录校验数据和判断状态 → 保存证据、收据与命令变更。已接收消息先返回保存的响应，不能因处理器升级收紧 data 校验而把原 ACK 改成 400。

已知命令的已接受结果、冲突结果、提前结果的规范化内容及首次响应保存在长期证据中；短期收据清理后仍能返回一致响应并阻止重复应用。P1 不自动清理命令或结果证据。404 不形成永久负缓存，命令后来合法存在时允许重新判断；400/413 不建立业务结果，503 整体回滚。

命令及长期证据不能被可靠终态清理级联删除，也不能依赖可靠消息行永久存在。关联保存稳定的投递身份；旧消息已清理时查询和结果重报仍依靠命令/证据工作，重复创建入口不得重建发送义务。摘要计算失败（例如 JSON 数值 `1e400` 解析后成为非有限数）映射为脱敏 400，不形成永久 503 毒消息。

首次合法 Result 在投递 DONE 已清理后到达，只要命令仍有合法派发/接纳依据且未封锁，仍可在命令事务内应用并 ACK；`settle=False` 本身不是回调失败。可靠行存在时在同一事务复核其实际状态并按 §5 处理，不能把“已终态”与“已被清理”混为一谈，也不能为 settle 创建替代消息。原附录版本的解析能力若缺失，新结果返回 503 并报告本地装配错误，不按新版本附录判 400；已保存的结果仍返回原响应。

### 6.2 公开调用与结果消费

- 命令创建是事务内 service 入口：消费方传业务调用身份、设备、动作和附录参数；调用方负责提交。P1 不额外开放生产 HTTP 发命令接口。
- 查询 service 按 command_code 或业务调用键返回命令状态、是否收到 ACK、设备报告的结果、暂停/封锁原因和是否需要人工核对；消费方受自己的权限和业务归属约束。不能返回可靠层模型作为业务接口。
- 结果回调只保存证据并应用命令自身状态；P1 不在回调内扣库存或任意调用外部服务。消费方通过公开读取接口取结果，在自己的事务用 `(consumer, command_code)` 等持久唯一键保证只推进一次。P1 用一个测试消费方验证重读不重复推进，不引入结果订阅总线。
- ECS 命令 SUCCESS 是设备报告的事实，是否足以推进具体业务由消费方按冻结对象及业务合同决定；不凭 ACK、Status 或可靠层 DONE 代替。

### 6.3 必须完成的边界

P1 包含 P0 所需的底座扩展、测试路由提供者、ECS 协议适配器、命令持久化、发送生命周期接线、结果 HTTP 入口、查询服务及迁移。没有命令模型和状态门禁时，不单独开放一个“把所有合法结果 ACK 掉”的结果入口。

P1 不包含正式设备附录的批量接入。使用一个隔离测试附录把机制闭环跑通；真实动作必须另有确认的附录和受控路由提供者。Status、具体事件处理器、本地交互式 ECS 控制台与真实设备验收属于 P2；这些未完成不妨碍 P1 机制验收，但 P1 通过不能写成 ECS 生产可用。

| A21 | 获取客户端或等命令锁直到租约/窗口过期时不发网；旧 token 不能复活；门禁续租与恢复竞争只有一个获胜；陈旧 finish 不先修改命令投影 |
| A22 | HTTP 在发送窗口截止后才返回合法 ACK 时仍进入 WAITING_RESULT；返回明确未接纳则 EXPIRED；未知则 HELD，不因 TTL 丢响应或取消物理动作；Result 先落终态后迟到 ACK/明确未接纳应答及 NOT_SENT 依据不丢失，经围栏外旁路保存，矛盾时标记待核对 |
| A23 | 一条 ECS 恢复/到期端口持续失败或命令被锁，另一条 ECS 与 WMS request/Transport 仍可领取结算；失败候选不永久占满批次；满批行锁冲突、仅 ECS 表锁等待、连接池占用及端口等待/取消时，恢复与到期共享同一整轮 deadline，健康消息在预算及有界清理后获得领取机会；验证首次命令锁前超时、零剩余预算不禁用超时、失败事务及状态不明连接不被复用；数据库整体不可用不伪报已隔离成功 |
| A24 | 重启时删 target/缺适配器但生命周期可用，快照消息持久暂停；缺生命周期本身时不发送、不提交分裂投影且报告不可用；旧未服务 STATIC 仍按原约定保留 |
| A25 | 可靠 DONE 清理后首次 Result 可按命令依据应用；清理与 Result 并发不误拒绝；长期证据不级联删除；不同结果不覆写已应用终态，普通消费不自动撤销既有业务 |
| A26 | 静态与动态目标混合运行时，两种客户端均能发送且统一关闭；Transport 无配置 settle、旧未服务目标、WMS 提示截短及 ECS 提示不截短分别符合 §5.4 |

## 8. 实施影响范围与迁移约束

| 位置 | 已实现的 P1 改动范围（供应商/部署验收另列） |
|---|---|
| `app/reliable/types.py`、`config.py`、`outbox.py`、`sender.py`、`delivery.py`、`store.py` | 快照、显式地址模式、HOLD/HELD、暂停、发送生命周期端口、恢复/结算与既有语义兼容 |
| `app/models/reliable.py`、`migrations/versions/` | 快照及暂停字段、状态/排期约束；旧行默认保留静态 RETRY 行为；一条 Alembic head |
| `app/reliable_runtime.py`、`app/main.py`、按地址客户端提供者 | 注入端口与生命周期装配；不在运行中改全局 base_url 或适配器表 |
| ECS 接入包、`app/models/`、模型导出 | 命令、结果证据、设备路由端口、协议分类、事务服务和公开查询；具体文件拆分留给实施计划 |
| 新结果控制器、`ecs_callback` 的可复用校验工具 | 独立 Result wire，复用共享底座；不塞进 WMS operation 或 Event 处理器注册表 |
| `tests/reliable/`、ECS 接入/controller 测试、migration 测试及公共 fixtures | §7 行为及 PostgreSQL 并发；不从一个测试文件导入另一个测试文件 |
| `.env.example`、接入指南、必要运维说明 | 显式 ECS 启用条件/窗口/资源容量；旧 Swagger 示例与新基线的差异说明；不写真实地址或凭据 |

迁移必须保留旧消息及身份，不重建已有消息或改写其物理结论。新增字段可空/默认值保持旧数据可读；新 ECS 消息和 HELD 只能由支持它们的新发送器处理。首轮发布必须协调停止旧 Sender、迁移后再启用新版本，不允许旧进程把新记录按旧策略发送。部署库升级与真实接入步骤仍未在本轮执行。

“旧进程”包括所有可能运行 Sender/维护的 API 实例及相关 worker/beat；不能只停一个入口。新快照消息出现后，回退到不认识快照/HOLD 的旧程序也必须禁止其连接并恢复这些记录；先形成保留命令身份与证据的回退方案。存在快照、HELD 或新证据时降级拒绝而不截断/删除。P1 的迁移验收应含混合旧静态数据与新快照数据，不声称未经验证的滚动升级或直接二进制回退可用。

## 9. 外部接入

本方协议实现与开发测试已结项；供应商实际字段/错误矩阵、D及跨重启保证、来源控制、现场容量和生产验证独立于开发，见[真实ECS接入清单](../../integrations/ecs-acceptance-checklist.md)。新命令统一W=300秒，不再逐部署配置窗口。没有结果纠正权威时继续保留冲突、人工核对，不自动改终态。

来源认证尚未实现时，持有有效command_code和device_code者可能伪造首个终态；实际开放Result前须落实来源控制，不能将UUID当认证。该风险与外部接入分开记录，不将未做生产验证当作开发缺陷。
