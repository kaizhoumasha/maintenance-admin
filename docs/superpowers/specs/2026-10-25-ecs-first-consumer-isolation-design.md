## 1. 目标与选择

在一个明确的消费项目内，以一个设备、一种动作验证：业务事务登记 → 原路由授权 → 唯一 Sender → 模拟 ECS → Result HTTP → owner 查询 → 业务事务幂等消费。完成后只称“该消费场景隔离接入通过”。

| 路径 | 收益与代价 | 决定 |
|---|---|---|
| 首个消费项目隔离接入 | 验证设备目录、授权、附录、业务身份和结果消费的实际接缝；依赖项目与业务输入明确 | 用户选择的推荐方案 |
| 先完善模板通用查询/告警 | 改善运维可见性，但不能证明真实目录、附录和业务消费接得上 | 场景需要的只读查询随接入完成，通用告警后续处理 |
| 批量设备、Status/Event 与控制台并行铺开 | 需要更多合同与业务规则，扩大验证范围 | 不纳入本阶段 |

仅使用现有 P1、现有依赖和消费项目的认证/事务约定，不建立第二个发送器、重试器或结果订阅总线。Status、具体 Event、自动取消/纠正、强制重发、解除 HELD 的写接口、生产管理页面和实际部署均不在本阶段。

## 4. 闭环与不变量

```text
可信业务意图 + 当前业务许可
  → 调用方事务：保存业务映射 + EcsCommands.create + outbox → 提交
  → 唯一 Sender：借客户端 → 锁命令/原授权/消息 → 登记尝试并提交
  → 单次 HTTP 到回环模拟 ECS（事务外）
  → Result HTTP：校验原命令/原附录 → 证据+收据+投影+settle → 提交后 ACK
  → 消费方事务：owner 查询已应用结果 → 保留消费唯一身份并更新原业务 → 提交
```

1. 调用键表示同一业务调用；技术重试不换号。新独立意图按当前事实和授权决定，不被旧失败/HELD 永久封锁；也不能换新调用键规避原命令的未知状态。
2. 业务映射保存 command_code 与原业务对象/意图身份。owner 来自可信装配，不接受外部请求任意指定；映射不能因当前设备绑定变化而指向另一轮业务。
3. 改址只影响新命令。原路由授权校验不解析新地址；待生效的 B 不替代仍有效的 A，新命令继续使用 A；本次新建无法取得唯一、有效且允许该动作的配置时拒绝创建。A 已撤销而 B 已生效且获准时，新独立意图冻结 B；旧调用重入仍核对输入并返回原命令，旧命令冻结 A，在原授权撤销先提交的发送门禁中不得发送，也不得改投 B。A→B 生效不等于撤销 A，显式撤销与门禁提交按现有锁序串行化。
4. 命令、业务登记和 outbox 同事务；Result 只处理命令及证据，不在回调内推进库存/业务或调用外部服务。
5. 消费仅依据 `CommandView.result` 中已应用结果，分别执行 I6 确认的 SUCCESS/FAILED 业务规则；ACK、DONE、Status、等待时长和日志恢复都不能代替业务完成。
6. 消费唯一身份至少包含 consumer 与 command_code；唯一约束/现有等价机制与业务更新同事务，失败一起回滚。重试读取原结果，不回发设备命令。业务对象、原映射/版本及当前许可的校验与业务写必须由 I6 确认的业务行锁、版本条件更新或等价机制保护，不能仅凭事务内先读后写。取消、换绑或版本变化先取得推进权并提交时，消费不得按旧读值更新业务或标记消费完成；消费先取得推进权并提交时，后续变更按已确认状态迁移处理，不覆盖已提交事实。条件更新失败须回滚本次消费完成标记与业务写，保留原结果及核对原因。能复用既有消费记录时不另建表。
7. 消费判断时已存在封锁/矛盾，或原业务映射/当前业务许可不成立，则停止该次推进并保留原因；不删除设备结果。读取后到达的 ECS 结果矛盾是迟到证据，不自动撤销已提交业务；这不豁免第6项对业务取消/换绑/版本变化的并发保护。若 I6 要求消费与所有迟到冲突严格串行化，须另行设计公共事务接口，不能绕过 DTO 私锁底座 ORM。
8. UNKNOWN/租约中断保持 HELD；合法匹配 Result 仅在 P1 允许的状态解决未知。提前结果、身份冲突等封锁不能靠再次提交、改址、Status 或普通 resume 解除。
9. `timeout`、HTTP 超时、发送窗口、结果等待监测四者独立。等待结果无自动失败/重发；长期证据保留与短期收据清理仍按 P1。
10. 脱敏、Sender 独立降噪/恢复、WMS STATIC 的原重试/事务语义保持；复用现有回归证明，不把 ECS HOLD 规则扩成全局规则。

## 5. 最小只读排障与操作边界

优先复用消费项目现有权限和查询入口，展示业务映射、command_code、命令/投递状态、是否实际 ACK、已应用结果、hold_reason、needs_reconciliation。没有现成 HTTP 查询需求时先用 service；不为隔离验收新增生产命令触发页。

HELD 与长期 WAITING_RESULT 必须有核对责任人和记录位置；本阶段可交付操作说明与受控只读查询。通用扫描告警、通知渠道与阈值独立留待现场 SOP 确认后设计，不能给出“模板已自带告警”的承诺。原始请求/响应证据仅在批准的存储和权限下查看，不复制到普通诊断日志。

## 6. 隔离验收矩阵

下表全部为待执行要求，测试必须从业务 service、Sender、HTTP Result 与公开查询入口观察完整状态。

| 编号 | 场景 | 通过条件 |
|---|---|---|
| V1 | 同调用键重入/并发、不同输入 | 一个命令与发送义务；冲突不新建；原身份/时间/字节不变 |
| V2 | 业务登记、命令、outbox 任一步失败 | 全部回滚；外层其他已授权事务行为保持；无半条可发送记录 |
| V3 | 目录缺失/歧义/没有有效配置/无动作许可 | 拒绝分支不创建命令/消息；原授权撤销则门禁不发送；UNKNOWN 授权 fail closed |
| V4 | 待生效配置、改址、撤销与发送竞争 | 待生效 B 不替代有效 A，新命令仍用 A；B 生效且获准后，即使 A 已撤销，新独立意图仍冻结 B；旧调用返回原身份/字节/A，撤销先提交的旧命令门禁不发送、不改投 B；显式撤销及锁先后满足 P1；历史失败不阻断获准的新意图 |
| V5 | ACK、明确未接纳、429、未知与重启 | 接纳只等待结果；安全重提保持原身份/字节且不早发；未知重启保持 HELD；不额外调度 |
| V6 | Result 先于 ACK、SUCCESS/FAILED、重复/矛盾 | 只应用符合原身份/附录/状态的结果；重报首响应一致；不伪造 ACK、不覆盖既定结果 |
| V7 | 原附录缺失、事务失败、短期记录清理 | 新结果503且零副作用；恢复原版本可重试；已存结果长期重放、不重建消息 |
| V8 | 重复/并发消费、业务更新失败 | 一次业务更新；消费记录与业务一起提交/回滚；消费重试不创建设备请求 |
| V9 | 跨 owner、陈旧映射、业务取消/换绑/版本变化竞争、结果冲突 | 越权不可见；对每类业务变更验证两种取得推进权的顺序：变更先提交则消费无业务效果且无消费完成标记；消费先提交则后续变更遵守已确认迁移、不覆盖已提交事实。版本条件失败与业务写失败均回滚本次消费标记；原结果/证据保留，不重发命令。已有结果冲突不推进，消费后迟到结果冲突只进入核对、不自动撤销业务 |
| V10 | 协议与容量异常 | 字段/大小/timeout 按冻结附录；客户端取消/关闭/容量有界，非法响应不误认成功 |
| V11 | 混合 WMS/ECS 与安全日志 | ECS 单条故障不永久阻断健康 WMS；原 WMS 重试/settle 保持；日志无载荷/SQL/凭据，独立降噪/恢复通过 |
| V12 | 隔离启动及清理 | 仅连接本次一次性库/队列和回环模拟器；无现场请求；仅清理本次资源；默认主应用仍未接入真实设备 |

最低验收证据：SQLite 快测 + 一次性 PostgreSQL 的事务/唯一键/锁竞争 + 一次性 Redis 的相关运行回归 + 回环 HTTP 全链路 + WMS 兼容回归。明确保存命令、退出码、基线、通过/跳过数和资源清理结果；不能凭 mock ACK 或单函数覆盖率宣布端到端验收。
