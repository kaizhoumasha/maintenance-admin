# DEVELOP 窄范围性能优化设计

## 目的

降低当前 `develop` 在 pending 扫描和后台列表查询上的数据库开销，同时保持现有业务推进、回调唤醒、重试和结果语义不变。

本批处理三类已确认的根因：

- SMT AUTO / SMT 手工在整轮推进期间长时间持有只读快照。
- AUTO 与粗分扫描器反复读取未到期或已完成历史记录。
- 用户、设备、工作线列表接受无限深的 OFFSET 分页。

## 范围

包含：

1. 将 SMT AUTO 与 SMT 手工扫描拆成“短事务取得本轮固定候选 ID 集合”和“事务外按临时文件批次读取 ID”，不在推进记录期间保持 REPEATABLE READ 快照。
2. 为实际 pending、未消费报告、已到达未终结以及粗分到期队列增加与查询条件匹配的索引；粗分候选查询排除尚未到期的记录。SMT AUTO 当前没有可靠地维护 `next_check_at_ms` 的事件边界，因此本批只增加其候选索引，不改变 AUTO 的推进条件。
3. 为旧式 OFFSET 分页增加最大偏移保护。本批采用 `MAX_OFFSET = 100_000`，超过后返回现有 INVALID_REQUEST 错误；不改变第一页和正常浅分页响应格式。
4. 为上述行为补充回归测试和迁移测试。

不包含：

- Celery 业务任务去重或 single-flight。
- worker 数据库引擎复用。
- 审计写入异步化。
- API / Sender 连接池重新配额。
- 现场设备、WMS/ECS 协议或生产数据清理。

## 方案与取舍

### 方案 A：只增加索引

改动最小，但无法解决扫描器在整轮处理期间持有快照，也无法阻止未到期记录进入业务事务。只能缓解部分 I/O，不能完整解决根因。

### 方案 B：候选筛选、短快照和深页保护（采用）

保持现有游标和上界语义，只缩短快照生命周期，在 SQL 层筛掉当前不应执行的记录，并限制不可控的深 OFFSET。不会改变业务推进顺序，也不引入新的调度组件。

### 方案 C：重做后台调度

同时引入业务级任务合并、worker 常驻引擎和新的唤醒协议，长期收益更大，但会改变任务并发边界，应该单独设计、压测和验收，不与本批查询优化绑定。

## 关键行为

- 本轮候选 ID 在一次只读事务中按有界 keyset 批次写入临时文件并固定，事务关闭后按文件批次读取，避免任意字符串 ID 的字典序上界误把新记录混入当前扫描，同时不把整个积压队列留在 worker 内存中。
- 记录是否到期由数据库条件决定；事件唤醒仍可立即推进新结果，Beat 仍负责兜底。
- `next_check_at IS NULL` 的记录继续可扫描；有未来 `next_check_at` 的记录留给到期后的扫描。
- 若未来等待中的粗分作业已有更高代次的货架准备，候选查询仍纳入该作业，让原有准备到达唤醒语义立即生效。
- `MAX_OFFSET` 只限制旧式页码接口；游标分页接口不受影响。
- 索引会同时更新 ORM 模型定义和 Alembic 迁移，保持模型与实际数据库一致。

## 验收

- 新增测试先在未修改代码上失败，证明：未到期记录不会进入候选页、深 OFFSET 被拒绝、扫描上界事务已结束后仍能按游标推进。
- 目标测试通过后运行受影响业务、分页、迁移和架构测试。
- Ruff 检查通过，Alembic 保持单 head。
- 不以未运行的真实 PostgreSQL/Redis 压测结果宣称生产吞吐提升；生产索引收益仍需在隔离数据库上用 `EXPLAIN (ANALYZE, BUFFERS)` 验证。
