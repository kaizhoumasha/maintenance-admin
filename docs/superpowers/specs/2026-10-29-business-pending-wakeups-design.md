# 按业务唤醒与统一待办推进设计

## 目标与授权

用户已选定“按业务唤醒、复用待办推进”，并授权更新公共约定、设计与计划后在当前功能分支直接实施。业务开发者只登记业务及待办入口、编写受理与推进规则，平台承担结果路由、提交后通知和 Celery 装配。仅 MOCK/内部验收，不提交、推送、合并、部署或访问现场。

## 方案与取舍

- 采用按业务通知：通知只携带 business_code，立即执行该业务原有的分页待办入口；Beat 每 5 秒调用同一个任务、相同入口。省去逐条结果反查和各业务的任务装配。
- 比较过统一持久业务实例关联的精准通知：扫描较少，但要新增关联机制和更多维护合同，本轮不采用。
- 扫描范围扩大会产生真实成本。本轮记录 1/25/100 条待办与 1/10/20 次通知的遍历数量、外部意图数和耗时，不用脆弱时间阈值冒充性能保证，不新增通知合并、锁或恢复表。

## 唯一开发用法

需要异步推进的业务在原 composition 声明 `PROGRESSION = "scan_pending"`，该名称指向 build_service 返回服务中可无参调用的异步方法；没有异步推进的业务可省略该声明。catalog 校验声明，runtime 校验并绑定方法。开发者沿用原事件、请求和命令声明，处理器只在当前事务保存收据、事实与 pending。

平台通过已校验的 RegistrationSource 与 catalog 所属模块定位业务；WMS 请求操作使用注册源，ECS Result 使用原命令 owner_domain，并要求该业务已声明推进入口。不能按 operation 名称前缀猜归属；local/平台演示、未知或未登记业务不触发正式推进。

允许共享任务装配与调度壳，替代旧的“不设通用业务 worker”的宽泛约束；调度壳不查询业务表、不消费结果、不拥有业务推进事务或第二 Sender。它只创建本次任务的工厂和生命周期资源，并调用声明的业务待办方法。引擎逐任务创建并在相同事件循环释放，连接可在本任务内复用，不复用 API 或其他任务的引擎。

## 提交与调用边界

- 通用 ECS Event 接收器成功调用正式处理器后，通过注入端口在外层提交后通知声明归属；WMS 入站回调的 Accepted 同样适用，拒绝、重放与回滚不通知。
- MessageStore 仅在非快照结果有效终态保存后，通过 `on_result(operation)` 通知；原租约失效、普通重试不通知。
- ECS Result 新证据与命令状态提交后通过 `on_result(owner_domain)` 通知；原收据重放不通知，ACK 仍非业务结果。
- API 注入上述端口。统一发布器 `enqueue_business(business_code)` 投递 `business.advance_pending(business_code)`；Beat 按 catalog 声明自动生成相同任务的 5 秒调度。
- 沿用共享 after_commit：保存点释放等待外层提交，回滚与关闭丢弃通知。即时发布使用独立连接/producer、retry=False、ignore_result=True、连接尝试 0 次重试、连接和 Redis socket 1 秒预算；失败不改变已提交事实或响应。共享任务声明与 Beat 调度选项均显式 ignore_result=True，Beat 的 Task.apply_async/send_task 两条发布路径都不订阅结果后端；Beat 的连接发布由 Celery 调度器管理。
- 粗分每次扫描固定本轮起始待办 ID 上界，避免持续入站使单次任务不结束；扫描期间新增待办由下一次通知或 Beat 处理。`scan_pending` 用短会话只定位候选 ID，不消费结果或为整轮扫描持有推进事务；每条记录的 `advance` 单独创建 session，在首条 SQL 前配置 REPEATABLE READ，并保留原锁序、身份与结果门禁。任务内连接复用不复用跨记录事务；持久 pending 是通知丢失及重启后的恢复依据，UNKNOWN/HELD 不自动换身份重发。

后续交付需让 API、worker、Beat 使用同一制品和新任务清单；旧通知丢失由持久待办恢复，不保留旧任务别名。本轮不执行该交付。

## 清理范围与验收

清除业务 request_advance/enqueue_advance 能力、advance_reference、scan/wms/ecs 引用路由、粗分专属即时和定时任务及其装配。只保留统一业务任务；旧设计/计划保留历史正文并链接本设计，不保留代码兼容入口。

验收覆盖：自动归属与跨业务隔离、正式应用装配、三点提交与回滚、发布失败仍 ACK、重复/并发通知、重建恢复、分页与阻塞待办不饿死后页、代表性待办量及通知密度、原 Celery/Kombu 有界发布合同。全量测试使用独立数据库和 Redis、回环 MOCK；无数据库迁移。

原三份已暂存计划内容和 index 保持原样；历史部署记录、交付包和其他本地文件保留。既有制品与新设计分开，本轮不声称已部署或完成现场验收。
