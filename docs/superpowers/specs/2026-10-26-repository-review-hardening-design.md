# 后台正确性与开发者入口优化 SPEC

**状态：已实现并完成本方自动化验证。** 本文保留五项稳定合同及验收条件，原评审与执行过程已外移；提交、推送与 PR 按显式交付指令执行，合并与部署另行授权。

## 1. 目标与现状

面向管理员、普通开发者和后台维护者，修复已复现的权限并发、会话撤销和异常诊断缺口，移除无必要的权限声明限制与历史文档入口。按多管理员、多请求、多进程并发使用评估；不引入新表、配置开关、兼容层或依赖。

合同基线：`develop@1ef1725da7d61d0d0e912066e524c5739960b88f`。回归入口见[开发测试](../../testing/README.md)，验证结果只认对应代码与实际执行，不沿用历史 CI 认证新增行为。

| 编号 | 优先级 | 修复前问题与根因 | 目标 |
|---|---|---|---|
| R1 | P2 | `set_role_permissions`、`set_user_roles`、`update_user`：三个入口修改后检查管理员数量，只锁单个目标；两个不同目标的事务均可通过检查，最终无管理员 | 修改与检查受同一事务级并发保护 |
| R2 | P2 | `session_service._ISSUE_TOKENS`：每次签发用新令牌 TTL 覆盖整个索引 TTL；缩短配置后索引先过期，全部登出漏撤销旧令牌 | 索引不早于其有效令牌失效 |
| R3 | P2 | `send_one`、`send_snapshot`：异常被转换为状态并正常返回，Sender 无法观察异常；仅有状态日志，没有安全异常诊断 | 保留状态决策，同时可定位原因和阶段 |
| R4 | P3 | `require_permission`：同码第二次调用 `require_permission` 导入失败，迫使开发者共享依赖对象或拆分权限 | 同一业务权限可保护多个路由 |
| R5 | P3 | `README.md` 引导按历史指南开发；历史开发路线图包含已过期的实现状态与过程记录 | 当前入口只引用有效合同；过程归档在仓库外 |

R1–R3 修复正确性与排障缺口；R4 调整声明规则，不改变已有授权；R5 维护当前合同和开发入口。

## 2. 必须保持的边界

- 不改变现有 HTTP 请求/响应、错误码、权限码和 JWT 格式；最后管理员冲突仍返回 409，不能停用自己的规则保留。
- ECS/WMS 的报文、事务归属、幂等身份（重复调用对应同一义务）、冻结地址/字节/期限、退避、Retry-After、租约和证据保留不变。
- UNKNOWN 表示交付不确定，HELD 表示暂停等待核对；日志改进、重启、换址或换键均不授权自动重放。
- 不合并 ECS 与 STATIC/WMS 的重试决策，不删框架证据表，不再叠加调度器；不改变 HTTP、Sender、维护任务、Celery 各自的降噪和恢复状态。
- 新正式/调试 ECS 命令共享 W=300 秒，旧调用及存量命令保留原冻结期限；最低对端去重合同不变。
- 不迁移本机数据库，不连接真实 ECS/WMS，不执行 SEED，不修改本地配置、现有暂存区、其他改动或 stash。
- 生产、供应商与现场验收独立于开发，不作为本批次未完成任务，也不宣称由自动化测试证明。

## 3. 行为合同

### R1：最后管理员保护

“管理员”仍指活跃且经角色拥有 `admin:role:set_permissions` 的用户，不按用户名或角色名判断。

- `set_user_roles`、`set_role_permissions` 和 `update_user` 的停用路径，在目标对象加锁或产生写入之前，先取得同一键的 PostgreSQL 互斥事务级咨询锁（`pg_advisory_xact_lock`，不是 shared 模式）。咨询锁是数据库协调并发的固定锁标识，随事务提交或回滚自动释放。
- 固定顺序为“同键互斥事务锁 → 当前目标状态/对象锁 → 修改 → 最后管理员检查 → 原提交点”。锁键为项目内固定常量，不来自请求或配置；不能只在修改后的检查函数内补锁。
- 停用路径取得保护后重读目标当前状态；沿用原提交与 Redis 撤销次序，不顺带重构跨存储事务。非停用的普通资料修改不取得该保护锁。
- 三个入口造成的并发变更必须保留至少一位有效管理员；不能用进程锁证明多实例正确性。SQLite 继续承担单事务单元测试，不宣称验证 PostgreSQL 并发。
- 直接 SQL、运维脚本以及不经这些入口的写入不在此保证内；不顺带修复角色删除的其他已记录并发限制。

### R2：刷新会话索引

- 保留 `refresh:<jti>`、`user_refresh:<user_id>` 和原子 Lua 签发/轮换/撤销机制，不新增索引结构。
- 对仍有有效成员的索引，签发不得缩短它原有的剩余寿命；有限 TTL 取原剩余时间与新令牌寿命的较长者。不存在的索引按新令牌设置寿命；已有无过期时间的索引不得被此次签发缩短。
- 在同一次 Lua 执行中读取寿命、清理过期成员、校验并消费旧 jti、签发新令牌并更新索引；注意 Redis 的“不存在”和“没有过期时间”返回值不同。
- 单点登录继续撤销旧刷新令牌，多点登录保留有效令牌；同一旧刷新令牌并发轮换仍只有一次成功；全部登出后旧令牌及其轮换结果不能恢复会话。
- 不改变 access token 无状态且在原有效期内仍可用的约定。此修复防止继续丢索引，不自动找回历史已丢索引，不扫描或清空运行 Redis。

### R3：可靠投递安全诊断

- 两处异常收口复用 `app.diagnostics.log_exception`，固定消息为 `reliable delivery failed`，`component=reliable`；上下文只传现有白名单中的 `message_id=claim.message_id` 与 `target`，不扩张白名单记录报文或任意业务文本。
- 失败阶段采用固定值：`prepare`（解析目标/装配）、`build_request`（构建与校验请求）、`acquire_client`（动态客户端取得及释放）、`before_send`（发送前事务门禁）、`send`（调用客户端及校验返回类型）、`classify_response`（校验完整响应并分类）、`apply_outcome`（生成投递结果）。阶段只用于诊断，不作为状态决策输入。
- 异常诊断携带安全异常类型、代码位置与阶段；同一吞获异常不再向上抛出造成重复日志。保持原 `store.finish` 调用及事务顺序；诊断不新增提交、回滚或发送。两条路径的取消与 `store.finish` 失败继续传播，不能扩宽异常捕获；回归同时核对原租约、状态、证据及 SNAPSHOT 客户端借用释放（D3=A）。
- STATIC 仍生成原 `FAILED/LOCAL_ERROR`；SNAPSHOT 仍按原发送前/后判定生成 HELD 和不确定性。`PoolUnavailable` 仍走原有分支，不提升为新增故障。
- 不输出原始异常消息、SQL/参数、URL 凭据、令牌、请求/响应正文；不新增消息级计数器、日志表或另一套降噪机制。

### R4：权限复用

- `require_permission(perm)` 接受同一合法权限码的多次声明；移除重复声明异常，不增加缓存或依赖工厂。
- 保留三段式格式校验、使用过的权限码集合、与 `INITIAL_PERMISSIONS` 的完整性检查，以及每次请求的数据库鉴权和原审计动作。
- 不改已有路由权限映射，不合并权限码，不更改角色授权，不要求重新 SEED；更新 README 与旧测试中“一码一路由”的表述。OpenAPI 回归按每条路由的权限依赖核对 403，同码多路由不再受唯一权限码数量约束；测试路由、注册集合及缓存须隔离（D2=A）。

### R5：当前入口与历史归档

- README 保留当前 ECS 教程/参考与可靠投递实验入口，不再要求按历史路线图任务表开发。实验中的环境准备链接改指当前测试说明，缺少的必要说明只保留一处。
- 先提取 历史 ECS/Transport 开发指南 中当前参考文档尚未覆盖的有效合同，再将原文迁出仓库。不能以删除文件丢掉仍有效的 Transport 合同。
- 一并替换该指南在 `docs/reliable-transport-lab.md`、ECS 命令/事件设计及事件 PLAN 中的引用；当前 ECS 状态按 PR #24 已合并的基线事实修正。
- 扫描现有 7 份 PLAN 的状态与本批引用链。只有已完成且仅含过程/历史证据的记录迁出；含当前有效合同的内容先归并，不把所有设计文件按日期批量删除，不重写旧验证结果为新证据。
- 历史文件迁往仓库外的受控归档；归档清单记录原相对路径、基线提交与 SHA-256，重名时不覆盖旧归档。仓库不保留副本、软链接或要求 AGENT 读取归档的入口。
- 版本化当前参考文档不依赖任何开发者个人目录才能读通。本 SPEC 实施结项后只保留稳定合同摘要，过程记录同样外移，不滚动追加执行流水。

## 5. 验收条件

下表为 15 组行为场景，可参数化合并到现有测试；组数不是新增测试函数或 pytest case 数。不得为凑数量复制已有回归。

| A1 | 不同管理员并发移除角色 | 两笔事务完成后仍有管理员，最后一次破坏性修改冲突并回滚 |
| A2 | 不同角色并发移除管理权限 | 同 A1；不以同一目标行锁代替验证 |
| A3 | 停用与角色/权限移除交叉并发 | 参数覆盖停用×角色、停用×权限及两个互相停用；守卫不被不同入口绕过 |
| A4 | 合法修改、拒绝和回滚 | 非最后管理员修改成功；原 400/404/409 保持；失败后下一事务可继续，无锁泄漏 |
| A5 | 缩短/延长刷新有效期 | 索引覆盖旧、新有效令牌；全部撤销后两者均不能再次刷新 |

## 6. 实施顺序与验证

顺序为 R1 → R2 → R3 → R4 → R5 → 统一复核：先恢复安全与正确性，再补排障能力，最后更新稳定行为的开发入口。五项没有互相依赖的新接口，可分别验收；不要求五份 SPEC 或五套新夹具。

- R1 用一次性 PostgreSQL、R2 用一次性 Redis，通过公开服务/API 固定失败行为，再修复。并发测试复用事件、数据库等待观测和有界超时，不靠长睡眠碰时序。
- R3 扩展真实 Outbox→claim→send_one 路径；R4 用独立测试路由验证鉴权。测试辅助放 `tests/helpers.py` 或 `conftest.py`，测试文件不互相导入。
- 定向执行相应 `tests/services/`、`tests/controllers/`、`tests/reliable/test_delivery.py`、`tests/core/test_permission_code.py`、`tests/core/test_global_diagnostics.py` 和 `tests/integrations/ecs_command/` 的已有测试；HTTP/Celery/Sender 诊断回归复用原入口。
- 设置显式 `TEST_DATABASE_URL`、`TEST_REDIS_URL`，仅指向本轮一次性资源；最终运行 `uv run ruff check .`、`uv run ruff format --check .` 和 `uv run pytest -ra`。测试库迁移只发生在一次性 PostgreSQL，不是本机运行库迁移。
- 只补实际覆盖缺口。应用代码改变后不沿用旧 CI 作为当前认证；完整测试统一运行一次，之后仅在改动、失败或未解决疑点出现时重跑。文档只核对内容、链接与归档完整性。
- 收尾报告列出定向/全量通过与跳过原因、15 组条件的证据、实际 diff、资源清理、原暂存区和 stash 保留情况；不自动提交、推送、合并或部署。

工作量仅为规划估算：R1 2–4 小时，R2 1–2 小时，R3 1–2 小时，R4 0.5–1 小时，R5 1–2 小时，统一验证与复核 1–2 小时。未实测开发耗时；不将其写成完成承诺。

## 7. 回退与交付门槛

无 schema 或 API 迁移。应用改动可按独立任务回退，但回退 R1/R2 会重新引入已知缺陷；回退日志补强不应触及状态机。若已有多个路由开始复用权限，不能单独恢复“一码一次声明”限制，否则启动失败，须连同调用方一起回退。

文档回退从仓库外清单或 Git 基线恢复，归档不覆盖、不自动删除；未获明确授权不对运行 Redis 执行修复、批量注销或数据恢复。

完成定义：A1–A15 均有通过或复用依据、完整测试结果可核验、无未解决的本批 P2、文档无悬空入口、diff 无无关改动。供应商/现场/生产验收不属于完成定义；真实交付、业务完成和物理完成不能由本批结果代替。
