# 业务提交后即时唤醒设计

## 目标与已选方案

默认采用“事件／结果提交后即时投递具体 Celery 业务推进任务，Beat 扫描持久待办兜底”。用户已选定该方案并授权在当前功能分支更新约定、设计、计划和实现，按 MOCK/内部验证验收；不提交、推送或部署。

已比较：应用进程直接推进可少一次队列传递，但需管理额外后台任务并隔离回调与 Sender；仅 Beat 轮询可恢复却增加正常阶段等待。当前选择复用已有 Celery worker；即时任务和兜底任务都调用同一业务 `advance`，持久待办是恢复依据。

## 事务与职责

- 新增共享 `after_commit(session, callback)`：只在最外层事务成功提交后执行同步通知；保存点释放仅合并通知，保存点回滚、外层回滚或未提交关闭均丢弃对应通知。通知失败记录安全诊断，不改变已提交的收据、结果或 HTTP 响应。
- 通知只带业务身份或原结果引用，不带条码、请求／响应原文或设备控制参数。通知发布使用 `retry=False`、`ignore_result=True`，不订阅任务结果后端；每次发布使用独立 connection/producer，连接尝试 `max_retries=0`，连接及 Redis socket 连接／读写超时均为 1 秒，不修改全局 Celery 配置或等待生产者池。失败交给既有持久待办和 Beat 恢复，不叠加消息发送重试器；这些 I/O 超时不等于 DNS/OS 调度下的硬实时总时限。
- 通用机制不导入 Celery 或具体业务。`MessageStore` 接受注入的结果通知端口；ECS Result 接收器接受注入的结果通知端口。应用装配将原操作／命令 owner 映射到具体业务任务。
- 业务通过注入的能力请求提交后唤醒自己的实例。API、worker 装配均注入同一发布函数；隔离测试可注入记录器。主应用正常装配默认启用，不按环境添加分支。
- Celery 的具体粗分任务可按扫码 ID、原 WMS message_id、原 ECS command_code 定位扫码，再调用原 `advance(scan_id)`。定位查询不消费结果，真正推进仍在独立 REPEATABLE READ 事务按原锁序、身份、绑定版本和公开结果读取接口判断。
- 不因通知本身推进，不在接收事务里调用后续业务，不在 Sender 中查询业务表，不增加通用业务 execute/worker、第二 Sender、状态机或新数据库表。

## 粗分三个唤醒点

| 提交的事实 | 唤醒引用 | 行为 |
| --- | --- | --- |
| 新扫码事实、收据与 pending 一起提交 | `scan` + scan_id | 登记原 WMS 验证请求 |
| 原 WMS 请求终态保存成功 | `wms` + message_id | 原决策有效时登记 MOVE_FORWARD 或等待 NG；异常保持待核对 |
| 新 ECS Result 证据与命令状态提交 | `ecs` + command_code | 原应用结果满足 SUCCESS、严格数量 1、无待核对义务才等待分配 |

WMS 决策是 Sender 获取的 HTTP 响应，必须在响应保存事务后通知，不能只改入站回调。普通发送重试不触发业务循环；非粗分操作及非粗分命令 owner 不投递粗分任务。重复回调沿用原收据和证据；重复 Celery 唤醒仍由同一 `advance` 幂等执行。提交失败、陈旧租约未写入结果等情况不通知。

## 恢复与验收

保留现有 5 秒 Beat 调度作为兜底，本轮不新增恢复周期配置。发布失败、提交到发布之间进程退出、任务丢失或 worker 重启时，原 pending 及原结果引用保留，由重建的具体任务扫描恢复；UNKNOWN/HELD 和业务待核对状态不因唤醒而自动重放消息。

测试覆盖：外层提交／回滚、保存点释放／回滚／外层失败、关闭未提交事务、通知异常不改变提交；三点不等 Beat 即发布且新会话可见事实；原 WMS 请求响应与 ECS Result 的真实保存接缝；发布失败后接收仍成功且重建后扫描恢复；真实 Celery/Kombu 发布接缝不进入结果后端、故障连接只尝试一次；重复／并发唤醒不重复生成原 WMS 请求或命令；正常链路由即时任务推进。使用独立 SQLite/PostgreSQL/Redis、内存 broker 与回环 MOCK，不请求现场对端。
