# 开箱机 WES 内部开发实施计划

**目标** 按工程评审 D1–D52 实现单一产品 MVP 的上下盖供料和工单交接，通过模拟对端及现场联调分别验证 WES 行为与设备事实。

**依据** [API 草案](../../integrations/opening-machine-api.md) · [概要设计](../../integrations/opening-machine-overview-design.md)

## 1. 实施边界

- 开箱机业务包保留 `service.py`、`source.py` 和 `settlement.py`。`service.py` 推进工单和交接，`source.py` 管供箱、补给和缓存，`settlement.py` 管额度、结算和差异。
- 复用业务目录、公共 WMS/ECS 接口、集成历史、RackDispatch 和 Transport。专属 operation、命令、事件和字段按已签认合同注册。API 和 worker 使用同一业务装配，模拟测试使用隔离业务目录和独立表。
- MVP 按工作线约定的一个产品投用，支持该产品续单与余箱复用。工单继续携带 `product_code`，用于核对开工绑定、箱码和补板。首期串行供箱、单层在途、工单级汇总。
- 提前备箱、主动补板和 WMS 逐箱扣账留待后续。

## 2. 状态和事务

| 工单阶段 | 推进条件 |
| --- | --- |
| 排队 | 已受理约定产品的原工单。按 `dispatch_sequence`、首次有效下发时间、`task_id` 排序。续单队首达到余量下限才领取，未领取时可改量或撤销 |
| 待开工绑定 | 开工通知引用领取时的有效版本和取偶后的执行目标。WMS 核对并持久保存绑定，收到匹配的 `RECORDED` 或 `DUPLICATE` 后开始供箱或余箱续用 |
| 运行中 | 选源、补给、扫描、取料和恢复沿原动作身份推进。每线只保留一个未结清额度 |
| 待完成通知 | 双侧达标且本地事项结清后冻结供料汇总。末箱空须由原额度最终 Result 同时确认实际离位。核实后的多料留箱续用，差异独立报告 |
| 待设备收尾 | 匹配当前有效汇总的 WMS 完成通知只转发一次。原汇总可能送达即可按约定推进。收到 ECS 可接下一单的原成功 Result 后完成 |
| 已完成或已撤销 | 保留原业务事实。旧回报继续归原动作，已撤销工单保持终态 |

建议三张业务表。名称及约束在实现时按现有模型规范确定。

| 模型 | 保存内容 |
| --- | --- |
| `OpeningTask` | 原工单与下发身份、排位及时间、领取时的有效版本、原需求套数与取偶执行目标、工作线、产品、阶段和双侧结算计数。同线最多一个已领取工单 |
| `OpeningCarton` | 原供箱、外箱码、盖型、原入线身份、实际占位、可用余量和待恢复状态。取料位与缓存各容一箱，已离位箱仍可用于原额度追溯 |
| `OpeningAction` | 原指令或请求、原箱、额度与结算、补给等待和原 ENTER 引用、恢复和消费身份。保留原结果、差异和经具名确认的调整依据 |

GET/PUT 和 SCAN2/3 由 ECS 上报 WES，按原额度、层序及事件引用保存到现有集成历史。逐箱耗用按原额度归集，工单切换后可追溯原账。供料结果只向 WMS 发送工单汇总和箱量差异报告。

回调同事务保存原事实和待推进记录。业务 `scan_pending` 复用提交后通知及 5 秒 Beat。推进用独立事务，首条 SQL 前设 `REPEATABLE READ`，按 WorkLine、Devices（ID 顺序）、所涉 RackJobs 和业务动作加锁，具体栈板操作遵守公共调度锁序。从公开读口核对原结果。同事务提交消费身份、状态、有效账及下一动作意图。发生 `40001` 时以新事务有界重试，耗尽保留原待办。

## 3. 实施与验收

### 任务 1 · 工单、续单与开工

- [ ] 在正式业务声明登记工作线角色、位置和初始入口。实现原下发、改量、撤销和续单余量复核。原操作重发保持原受理结果。
- [ ] 验证约定产品的工单可以排队、执行和续单。产品不匹配时返回 `422 / REJECTED`，不入队、不触发设备动作。
- [ ] 验证同线 `dispatch_sequence` 升序，序号相同按首次下发时间，仍相同按工单号。领取后锁定原单，后来高优先级工单留到下次选择。
- [ ] 验证正整数套数，1 套执行目标各 2 片。零、负数和非整数拒绝。版本 3 先到、版本 2 迟到时有效版本保持 3，排位和下发时间保持。用 PostgreSQL 验证改量、撤销与领取并发及 `40001` 恢复。
- [ ] 验证领取事务按 [余量下限](../../integrations/opening-machine-api.md#continuation-quantity) 核对队首。下盖余 10、上盖余 16 时，15 套保持未选中并可改量或撤销，16 套可领取。同盖型跨两个位置的余量相加。当前开工绑定确认前没有生产动作。
- [ ] 验证 WMS 在开工绑定时核对版本与取偶目标。版本 1 的原需求 5 套时，开工和汇总均为执行目标 6 套。验证错版本、错目标和迟到确认保持等待。回执丢失后沿原通知恢复，已保存原绑定的 `DUPLICATE` 可推进。

### 任务 2 · 串行供箱、扫码和设备联动

- [ ] 统一业务盖型 `cover_type` 为 `UPPER` 或 `LOWER`，校验请求的 `expected_cover_type` 用同一枚举。模拟 [ARM01 目标协议](../../integrations/opening-machine-api.md#fetch-carton)，验证报文只带 `source.cover_type`，上盖从 A 取、下盖从 B 取。盖型和来源工位不匹配时不下发，核对原指令与后续箱码校验、到箱、开箱和额度的盖型一致。
- [ ] 复用 ARM01 原 Result 和 SCAN1 事件。匹配一条有效扫码后通过 `decisions` 同步取决定。同码重报只查原请求，异码待核对，旧决定或未知响应维持原箱等待。
- [ ] 验证明确 NG 转发、ECS 重读失败后自主退箱及两者共用的恢复事件。人工取走且入料口释放前保持原占位，匹配原供箱和工位的回报后只恢复一次。
- [ ] 用 ARM03 `BIN_ARRIVED` 验证到位位置、箱号、盖型和原 ARM01 指令号与开箱授权匹配后只登记一次本箱首份额度。错误引用覆盖 ARM02 自身指令号和上一箱的 ARM01 指令号，另验证缺字段、其他工位和重报。ARM02 原 Result 单独保存。新箱到位先于前一额度最终 Result 送达时先保存，待原结果一次结算并释放原空箱占位后再核对新箱授权。重复旧结果不释放新占位。缓存移动按原成功 Result 更新占位。
- [ ] 现场联调确认 PLC 的 CCD 到位可取信号，并逐箱验证 `OPEN_CARTON.params.source_command_code` 与 ARM03 `BIN_ARRIVED.data.source_command_code` 都等于原 ARM01 指令号。

### 任务 3 · 缺箱补给

- [ ] 用现场预放的 A/B 栈板走首次取箱。ARM01 冻结 `start_operation_id`，ECS 按原绑定向 WES 报取空。WES 持久保存事件和待发送报告后 ACK，沿原报告向 WMS 交付。WES 转达 WMS 已持久收妥且 ECS 匹配原工位事件后才应答 PLC。原取空出现但尚未缺箱时保持正常供箱。
- [ ] 验证 C/D 堆满和 E/F 废料架满按同一 [工位事实报告](../../integrations/opening-machine-api.md#station-event-report) 交付 WMS，按工位归属。模拟 WMS 暂不可用、WES 重启和重复上报，原报告各只应用一次。现场验证三类 ECS 回调都发往 WES。
- [ ] 明确缺箱且未搬箱后才登记补给请求。测试证据缺失返回 WAIT，按 `retry_after_ms` 到期重新请求，通信未知仍沿原请求。覆盖迟到取空、同产品同轮次跨单引用及换板后拒绝沿用。
- [ ] 覆盖匹配设备侧清位证据后才释放原作业，公共 ENTER 传 `source.kind=RACK` 与原栈板号。注入只有取空或提交接纳、错工位、错原板或错轮次，继续保护占位。验证同工位连续两轮，只在匹配原 f0 成功且工位可取后各恢复一次取箱。
- [ ] 跑公共调度及受影响业务的现有离场回归。新增共享调度测试证明开箱机清位证据无法释放其他业务的栈板，原 `DEPART` 正确接纳后仍可释放。

### 任务 4 · 整层结算、异常与恢复

- [ ] 复跑 [同箱补取示例](../../integrations/opening-machine-api.md#ecs-quota-supplement-example)。首份额度取出 6 片、成功 4 片、NG 2 片，按原指令号结算一次。前一额度结清后，同一箱用新指令号补取 1 层，收到新额度的最终 Result 后结算一次。重报任一结果只保留两次结算和一份补取授权。
- [ ] 验证取满额度正好取空及提前箱空均由原最终 Result 同时回 `carton_departed: true`。留箱回 `false`。缺失或矛盾字段保持待核对。
- [ ] 模拟先 PUT 后 GET、明细缺失、单独冲突和重复。合法最终 Result 一次入账，明细可以按原额度及层序查询。验证额度、最终 Result 和逐层明细只在 ECS 与 WES 间交互，供料结果只向 WMS 上报工单汇总和箱量差异。模拟 ACK 后跨过命令样例时间及发送窗口，原动作保留并等待原最终结果。
- [ ] 验证早空 22/20、多料 22/24、取料失败后设备恢复及余量未知。数量未知等设备端核实，原占位与额度保留。外码 22 片、实到 24 片时，核实的 2 片留箱并在原额度结算时一次记为可用，独立报差异。延迟差异收妥回执，设备互锁满足时仍可按本侧缺口取料。本侧达标时，将余料计入下一单下限。
- [ ] 对实物或最终结果异常，验证按影响暂停、设备侧实物证据匹配、WES 具名确认、差额调整一次和有效计数同事务提交。设备未确认可安全续作时继续暂停。涉及已送达或可能送达的汇总由 WMS 按原号人工更正，WES 按核对结论恢复依赖动作。
- [ ] 验证双箱在位时按当前缺口继续取料，确认空箱离位后恢复另一侧缓存箱。注入当单达标侧才核实多料、箱体无法移入缓存且另一侧仍有缺口的情形，验证只走通用实物异常流程。双侧均达标时按汇总条件推进。

### 任务 5 · 工单汇总与端到端验收

- [ ] 模拟双侧达标，分别验证空末箱须由原额度最终 Result 同时确认实际离位、核实后的多料与普通余料一并留箱，工单汇总按原条件推进。逐箱记录归原额度，工单只发送一份有效汇总。
- [ ] 联调 WMS 按汇总的 `drawn_pcs` 记各工单实耗，按差异报告独立调整库存。22/24 多料场景跨两单取 22 和 2 片，交换两类报告到达顺序并重发，核实工单实耗和来源库存差异分别只应用一次。
- [ ] 验证匹配原汇总的完成通知先于 HTTP 回执时只转发一次。原汇总确认未发、明确拒绝或引用错误时保持待核对。原 ECS 成功证明可接下一单后释放工作线。
- [ ] 用模拟对端走完所选产品的连续两单，验证该产品的余箱复用。覆盖原 Result 丢失后重报、通知唤醒丢失由 5 秒扫描恢复，以及结果和补板并发消费。使用仓库现有 pytest、Ruff 和一次性 PostgreSQL 验证。
- [ ] 现场对齐 [首期接口事项](../../integrations/opening-machine-api.md#delivery)。请供应商同步 ARM01 接口文档及 ECS/PLC 解析，确认 `source.cover_type` 和两个枚举的实际工位，目标协议通过联调后接入。验证网关来源、PLC 取空应答、f0 放板可取、退箱、ARM03 自动清箱与 ARM02 对已开箱的自动送箱。核对设备联动无 WES/WMS 指令，取空时原额度最终 Result 带实际离位，末箱可在工单汇总前自行清走。验证 ECS 收尾可接单与原身份重报。延迟或丢弃 GET/PUT 回执，验证设备按单层互锁继续执行、ECS 沿原事件补报和 WES 一次入账。记录实际整箱节拍。
