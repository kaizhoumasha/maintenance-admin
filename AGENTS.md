# Repository Guidelines

## Working Principles

- **Think before coding:** state assumptions and tradeoffs. Clarify ambiguous interpretations or blocking uncertainty before implementation. Propose simpler approaches.
- **Simplicity first:** implement requested behavior only. Reuse existing patterns; avoid speculative features, single-use abstractions, and impossible-case handling.
- **Surgical changes:** every changed line must serve the request. Match surrounding style; avoid unrelated refactoring/formatting. Remove only dead code your changes create; report pre-existing issues separately.
- **Verify outcomes:** define success criteria. For multi-step work, pair each step with a check. Reproduce bugs before fixing; verify refactors before/after. Report checks and limitations accurately. Use judgment for trivial tasks.

## Project Structure & Module Organization

`enterprise-backend` is a Python 3.13+ FastAPI enterprise backend template for WMS, MES, WES, and other manufacturing applications, with shared administration and third-party/internal API integration capabilities. Keep domain business rules in the consuming projects and distinguish implemented capabilities from planned ones.

- `app/businesses/<business>/`: domain-owned definition/contracts/composition/service/models and thin registered entries. `definition.py` is immutable and standard-library-only; composition declares fixed `ENTRY_MODULES`/`MODEL_MODULES`, `COMMANDS=(Model, ...)` and a stateless factory. Catalog compiles command models internally and activates only the owning definition's role intersection; businesses never author compiled bindings/annexes. Explicit `catalog.entries()` is shared by API/worker; startup loads all formal entries and crosschecks contracts before local entries/resources/factories. The deployed catalog includes the approved coarse-sorting scan → WMS validation → first MOVE_FORWARD / Result stage; never fill it with test/dev/placeholder packages. Environment-specific validation resources belong to deployment/test configuration. See `docs/integrations/business-packages.md`.
- Acceptance uses the receiver-owned transaction for original receipt + business state + durable pending work. Result consumption belongs to a concrete business advance entry with Capabilities.session_factory supplied by API/worker assembly: create a new session, set REPEATABLE READ before its first SQL, then lock WorkLine → Devices in ID order → business action. Persist progress/consumed identities and versions/next outbox intent atomically; retry a serialization failure as a bounded whole transaction in a new session, retain pending work on exhaustion. Only public result readers may inspect framework outcomes; no direct ReliableMessage/TransportTask reads, generic business worker/execute or second Sender. Test business tables use independent MetaData and explicit creation/finally cleanup, never production Base/migrations.
- `app/controllers/` → `app/services/` → `app/models/`: routes, business rules/transactions, SQLAlchemy models.
- `app/schemas/`: Pydantic contracts; `core/`, `middlewares/`, `tasks/` under `app/`: infrastructure, middleware, Celery jobs.
- Default business progression is committed event/result → immediate concrete Celery task; Beat scans durable pending work as fallback. Use `app.transactions.after_commit` so savepoint release waits for outer commit, rollback/close discards notifications, and publication failures never undo committed facts or change ACK. API/worker assembly injects the publisher through Capabilities; generic receivers/Sender use injected result ports, never business imports or queries. Notifications carry identities only; publish with ignore_result=True, no publish/connection retries, and independent connection/producer with one-second connection/Redis socket budgets. Immediate/fallback tasks share one business `advance`; retain original delivery and reconciliation gates. See `docs/superpowers/specs/2026-10-29-business-commit-wakeups-design.md`.
- Coarse sorting wakes its concrete `coarse_sorting.advance_one` after scan acceptance, saved WMS decisions and ECS Results; `advance` / paginated `scan_pending` and the 5-second Beat scan share the same checks. Each task owns its factory and lifecycle-enabled outbox, never another Sender. WMS business NG preserves its response at `AWAITING_NG_STAGE`. Only an applied original SUCCESS with strict quantity 1 and no reconciliation obligation advances to `AWAITING_ALLOCATION_STAGE`; MOVE_FORWARD Result.data contains only actual_qty, without a fixed output-location gate. NG movement and allocation remain later stages.
- `app/diagnostics.py`: configuration-free safe error fields, origin and stack generation for HTTP, reliable maintenance and Celery. Use `log_exception` with a fixed message and allowlisted identifiers; never log raw exceptions, SQL, payloads or credentials. Each task owns its suppression/recovery state; diagnostics never change retry, transaction or delivery decisions. See `docs/logging.md`.
- `app/http_client/`: standalone HTTP client; no `app.core`, business, database, Redis, Celery, or FastAPI imports. single-request scope only (no retries, rate limiting, or application assembly).
- `app/reliable/`: protocol-agnostic outgoing-message outbox, leases, retries and TTL; uses only injected adapter ports. No business/protocol implementations, FastAPI, Celery or result-consumption API. Assembly lives in `app/reliable_runtime.py`; Celery only cleans terminal rows. Never stack another retry scheduler around these messages.
- `app/businesses/<business>/dev.py` + `app/core/dev_scenarios.py` + `app/controllers/dev*.py`: local-only (`ENVIRONMENT=local`) dev console (task submission) and built-in mock WMS; register scenarios with `@dev_scenario` and explicitly list the module in the catalog-owned composition.ENTRY_MODULES. Fixed platform demos use the shared manifest. See `docs/superpowers/specs/2026-10-22-transport-dev-console-design.md`.
- `app/controllers/ecs_callback.py` + `app/integrations/ecs_callback/`: generic ECS event receiver (`POST /api/v1/callback/event`: strict envelope, content-derived identity, durable receipts and ACK). Add a confirmed role event with `@ecs_event(name, device_role=ROLE, data=Payload)` in `app/businesses/<business>/ecs_event.py` or an `ecs_event/` package (one lowercase event-type filename per handler); explicitly list the entry in the catalog-owned composition.ENTRY_MODULES; `dev_ecs_event` is local-only. Handlers write only the current transaction; external intent goes through the outbox. Inject a runtime BindingResolver when assembling formal role handlers; role declarations do not query devices or Status. Coarse sorting registers its sole SCAN_COMPLETED handler through the formal catalog in every environment, using the configured database and migrated business table; startup never seeds test bindings. Local authenticated event debugging uses `/api/v1/dev/ecs/events` (registry-derived Swagger examples, original receiver delivery and digest query), with an injected read-only coarse projection. There is no separate local business handler, private event map, device-prefix dispatch or extra SQLite runtime; see `docs/integrations/ecs-event-debugging.md`. Unknown-event replay remains unimplemented. See `app/integrations/ecs_callback/__init__.py` and `docs/superpowers/specs/2026-10-24-ecs-event-callback-design.md`.
- `app/controllers/wms_events.py` + `app/integrations/wms_callback/`: generic receiver for peer callbacks (`POST /api/v1/wms/events`: envelope, idempotent receipts, snapshots). Add an operation with `@callback_operation(name, data=Payload)` on `async def handler(ctx, payload)` in `app/businesses/<business>/callback.py` or a `callback/` package with one file per operation, named after the operation (`a.b@v1` → `a_b_v1.py`, checked at registration) (explicit composition.ENTRY_MODULES plus catalog ownership; `dev_callback.py` only when local); see `wms_callback/dev_callback.py` and `docs/integrations/registration.md`. Do not name generic mechanisms with warehouse terms such as `inbound`.
- `app/integrations/wms_request/`: WES → WMS `decisions` / `facts` request endpoints (protocols `wms-facts`, `wms-decisions`), endpoint-level envelope/ACK classification and an operation registry. The formal coarse-sorting business registers `inbound.coarse_sorting.validate_bind@v1` on `decisions`. Add an operation with `@request_operation(name, Endpoint)` on a `RequestPayload` model in `app/businesses/<business>/request.py` or a `request/` package with one file per operation, named the same way (explicit composition.ENTRY_MODULES plus catalog ownership) and send only exact registered models with `WmsRequests.send(session, payload, operation_id=...)` inside the caller's transaction; confirm each operation against the WMS contract first. Both endpoints use the reliable outbox; local debugging (operation catalog, trigger, status, mock WMS) lives in the dev console (`/api/v1/dev/wms/requests`, demo operations in `wms_request/dev.py`); formal callers use `WmsRequests.get_result` to read original terminal responses and `TransportService.get_result` / `list_unclosed_predecessors` for applied outcomes and explicit predecessors. See `docs/integrations/outbound-results.md`; readers never write or own transactions, and multi-query consumption uses a caller-owned independent Repeatable Read transaction.
- `app/integrations/ecs_command/` + `app/controllers/ecs_result.py`: ECS P1 transactional commands and durable results. Formal businesses declare strict command models with `@ecs_command(..., device_roles=(...))`, expose only composition.COMMANDS, and call `create(session, owner=..., call_key=..., device_code=..., timeout_ms=..., command=Model(...))`. Platform startup uses catalog-compiled contracts with `configure_ecs`; local Swagger (`/api/v1/dev/ecs/commands`) auto-assembles the generic v3 contract and shared logical channel, with required `ecs_url` and `dev:ecs:send_real` permission for new registration. New formal/debug commands use exported `PROTOCOL_RETRY_WINDOW` (300 seconds); existing calls and messages retain original frozen deadlines. Trusted startup may merge `history_annexes` for original strict Result validation; old dev policies stay fenced. Freeze identity, bytes and origin; UNKNOWN/HELD never auto-replays, and Result/evidence/settlement share a transaction. STATIC/WMS behavior remains unchanged. See `docs/integrations/ecs-command.md` and its tutorial; real sending still requires supplier/site acceptance.
- Device/workline management is admin-only plus per-operation `asset:*` permissions. `GET /devices` and `GET /devices/{id}` return configuration only; detail state/manual refresh share `POST /devices/{id}/refresh` with `asset:device:refresh`, using generic ECS Status outside DB transactions and rechecking configuration/generation before returning. No device status jobs, periodic sync, observations table or status cache. Configuration deletion preserves route/command/result/evidence history and role send gates. See `docs/integrations/device-management.md`.
- Business declaration sources are only `app.businesses.<business>.<module>`; the shared `app.integrations.discovery` loaders merge catalog entries with `PLATFORM_FORMAL_MODULES/PLATFORM_LOCAL_MODULES`, never scan the integrations root. All three integration registries share `registration_filename(name)` (`lower`, replace `.`/`@` with `_`, append `.py`), import-time repair hints and source metadata. Local authenticated catalog: `GET /api/v1/dev/integrations/registry`. See `docs/integrations/registration.md`.
- `tests/`: mirrors application areas; `scripts/`: development/bootstrap tools.
- `migrations/versions/`: Alembic migrations (`YYYY-MM-DD_slug.py`).

Services own business logic. Register routers in `app/main.py`; export models from `app/models/__init__.py`.

## Build, Test, and Development Commands

- `uv sync`: install locked dependencies.
- `cp .env.example .env`: initialize configuration; do not overwrite existing settings.
- `docker compose up -d`: start PostgreSQL (25432) and Redis (26379).
- `uv run alembic upgrade head`: apply migrations.
- `uv run uvicorn app.main:app --reload`: start the API.
- `uv run celery -A app.tasks.celery_app worker -l info`: start workers.
- `uv run celery -A app.tasks.celery_app beat -l info`: start the scheduler (run exactly one).
- `uv run pytest`: run tests.
- `scripts/lint.sh`: fix/format with Ruff; review its diff. Check without edits using `uv run ruff check .` and `uv run ruff format --check .`.

## Coding Style & Naming Conventions

Use four spaces, type hints, `snake_case` functions/modules, and `PascalCase` classes. Ruff uses a 100-character line limit. Example: `services/user_service.py`. Raise `AppError(ErrorCode.X, ...)`; use shared error handlers.

## Testing Guidelines

Use pytest, pytest-asyncio, HTTPX; name tests `test_*.py` / `test_<behavior>`. Reuse `client`, `redis`, `admin` fixtures. Unit tests use SQLite/fake Redis; Celery runs eagerly. Integration tests require explicit `TEST_DATABASE_URL`/`TEST_REDIS_URL` for disposable stores; unset configuration skips tests, configured connection failures fail. PostgreSQL applies migrations. No coverage threshold. Cover changes and failures. Tests pin long-lived behavior contracts, not the change that introduced them: assert observable behavior through public entry points (HTTP, service functions), not private helpers or exact internal shapes. Prefer rules over snapshots (e.g. "every route with a permission documents 403", not a hard-coded response set per route). Keep regression tests for fixed bugs; do not keep one-off verification of a refactor, transitional states (e.g. "old parameter now rejected"), or fixture wiring smoke tests. Shared helpers live in `tests/helpers.py` or `conftest.py`; test files never import from each other. Name tests and comments by behavior, not by SPEC number.

## Commit & Pull Request Guidelines

Follow history: `feat:`, `fix:`, `test:`, `chore:`, concise Chinese descriptions, optional `(SPEC-015)` references. Keep commits focused. PRs should explain behavior changes, link issues/specifications, list validation, and identify migrations/configuration changes.

## Branching (Git Flow)

Baseline is `main` at tag `v0.1.0`; work follows Git Flow from there.

- `main`: released code only. Every commit is a release or hotfix merge, tagged `vX.Y.Z` (annotated). Never commit directly.
- `develop`: integration branch, always green (CI runs ruff and pytest on every push and PR). All new work branches from it.
- `feature/<slug>` (from `develop`, e.g. `feature/spec-017-dictionary`): merge back with `--no-ff` or a PR into `develop`, then delete the branch.
- `release/X.Y.Z` (from `develop`): only the version bump (`pyproject.toml` and `version=` in `app/main.py`), upgrade notes, and fixes. Merge into `main` with `--no-ff`, tag `vX.Y.Z` on `main`, merge back into `develop`, delete the branch.
- `hotfix/X.Y.Z` (from `main`): urgent production fix. Merge into `main` (tag) and `develop`.
- One Alembic head at all times: when two branches each add a migration, the later one to merge rebases its `down_revision` onto the new head.
- Agents work on `feature/*` branches created from `develop`, never directly on `main` or `develop`, and commit or push only when asked.

## Security & Configuration

Never commit `.env` or secrets; replace the example JWT secret. Review autogenerated migrations. Permission codes use `<module>:<resource>:<action>`; update `INITIAL_PERMISSIONS` and permission tests together.
